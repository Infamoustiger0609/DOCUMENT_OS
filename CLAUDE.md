# DocumentOS AI

## Stack

- **Backend**: FastAPI (Python)
- **Frontend**: Next.js (App Router, TypeScript, Tailwind CSS)
- **Database**: Supabase Postgres with pgvector for embeddings
- **File storage**: Supabase Storage (private `documents` bucket)
- **Text extraction**: PyMuPDF (native PDF text) + Tesseract (OCR fallback for scanned/image pages)
- **AI calls**: Groq API (LLM inference)
- **Deployment**: Render (backend deployed as a **Docker** web service — see [System dependencies](#system-dependencies) — + frontend)

## Environment variables

Backend reads these via `backend/config.py` (loaded from `backend/.env`, see `backend/.env.example`):

| Variable | Purpose |
|---|---|
| `GROQ_API_KEY` | Authenticates requests to the Groq API for LLM inference |
| `SUPABASE_DB_URL` | Postgres connection string for the Supabase database (pgvector-enabled) — separate from the two vars below, which are for Storage, not the database |
| `SUPABASE_URL` | Supabase project URL (e.g. `https://<project_ref>.supabase.co`), used by the `supabase-py` client for Storage |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase service role key — has full access to Storage (bypassing RLS), used server-side only to upload/download from the private `documents` bucket |
| `JWT_SECRET_KEY` | Signs/verifies the JWTs issued by `/auth/login` and `/auth/register` (`backend/auth.py`). Required — no insecure fallback, the app won't safely start without a real value. Generate with `python -c "import secrets; print(secrets.token_urlsafe(32))"` |
| `JWT_ALGORITHM` | Optional, defaults to `HS256`. JWT signing algorithm. |
| `JWT_EXPIRES_MINUTES` | Optional, defaults to `1440` (24h). How long an issued token is valid. |
| `ALLOWED_ORIGINS` | Optional, defaults to `http://localhost:3000`. Comma-separated list of origins allowed to call the API (CORS). See [Security](#security). |
| `SENTRY_DSN` | Optional, unset by default. Backend Sentry error tracking (`error_tracking.py`) — a no-op when empty. See [Error tracking (Sentry)](#error-tracking-sentry). |
| `ENVIRONMENT` | Optional, defaults to `development`. Tags Sentry events so local/staging/production errors are distinguishable. |
| `TESSERACT_CMD` | Optional. Full path to the `tesseract` binary — only needed on Windows dev machines where it isn't on `PATH` (e.g. `C:\Program Files\Tesseract-OCR\tesseract.exe`) |

| `LIBREOFFICE_CMD` | Optional, defaults to `soffice`. Full path to LibreOffice's headless binary — only needed on Windows dev machines where it isn't on `PATH` (e.g. `C:\Program Files\LibreOffice\program\soffice.exe`). Used by `/tools/docx-to-pdf`. See [Document tools](#document-tools). |

## Running locally

**Both services together** — from the repo root, run one of:

```powershell
.\dev.ps1
# or, if PowerShell's execution policy blocks it:
powershell -ExecutionPolicy Bypass -File .\dev.ps1
```

```bash
./dev.sh   # macOS/Linux
```

Either script starts the backend (`uvicorn`, port 8000) and frontend (`npm run dev`, port 3000) together, streams both logs into the same terminal prefixed with `[backend]`/`[frontend]`, and stops both on Ctrl+C. They assume `backend/venv` and `frontend/node_modules` already exist — run the manual setup below once first if you haven't. `dev.ps1` uses whatever's at `backend\venv\Scripts\python.exe` if present, else falls back to `python` on `PATH`; `dev.sh` does the same for `backend/venv/bin/python`.

Or run each service manually in its own terminal:

**Backend** (from `/backend`):

```bash
python -m venv venv
venv\Scripts\activate        # Windows
pip install -r requirements.txt
cp .env.example .env         # then fill in real values
uvicorn main:app --reload --port 8000
```

Health check: `http://localhost:8000/health`
Documents list: `http://localhost:8000/documents`

**Frontend** (from `/frontend`):

```bash
npm install
npm run dev
```

App: `http://localhost:3000`

## System dependencies

**Tesseract OCR** is required at runtime for image/scanned-PDF text extraction (`backend/extraction.py`, via `pytesseract`) — it is a system binary, not a Python package, so it must be installed separately in every environment that runs the backend:

- **Local dev (Windows)**: install from the [UB-Mannheim Tesseract build](https://github.com/UB-Mannheim/tesseract/wiki), then either add it to `PATH` or set `TESSERACT_CMD` in `.env` to the full path of `tesseract.exe`.
- **Local dev (macOS)**: `brew install tesseract`
- **Local dev (Linux)**: `apt-get install tesseract-ocr`
- **Render**: Render's native Python runtime has no way to install system packages, so the backend is deployed as a **Docker** web service using [backend/Dockerfile](backend/Dockerfile), which installs `tesseract-ocr` via `apt-get`. [render.yaml](render.yaml) already points the backend service at this Dockerfile (`env: docker`), so this happens automatically on every deploy — no extra buildpack or dashboard configuration needed for Tesseract specifically.

**Ghostscript** and **LibreOffice** were added alongside Tesseract for the `/tools/*` document-editing endpoints (see [Document tools](#document-tools)) — same "system binary, not a Python package" situation:

- **Ghostscript** (`/tools/compress-pdf`, and a dependency `ocrmypdf` shells out to for `/tools/ocr-pdf`): **Local dev (Windows)** — install from [Ghostscript's official releases](https://github.com/ArtifexSoftware/ghostpdl-downloads/releases) (the Windows installer needs admin elevation) and set `GHOSTSCRIPT_CMD` in `.env` to the full path of `gswin64c.exe`. **macOS**: `brew install ghostscript`. **Linux**: `apt-get install ghostscript`.
- **LibreOffice** (`/tools/docx-to-pdf`, headless `soffice --convert-to pdf`): **Local dev (Windows)** — install LibreOffice normally and set `LIBREOFFICE_CMD` in `.env` to the full path of `soffice.exe`. **macOS**: `brew install --cask libreoffice`. **Linux**: `apt-get install libreoffice-writer` (just the Writer component, not the full suite — all `/tools/docx-to-pdf` needs).
- **Render**: `backend/Dockerfile` installs both (`ghostscript`, `libreoffice-writer`) via `apt-get` in the same layer as `tesseract-ocr` — no separate deploy configuration needed.

## Database

- **ORM**: SQLAlchemy (`backend/database.py` sets up the engine/session from `SUPABASE_DB_URL`; `backend/models.py` defines the `Document` model).
- **Migrations**: Alembic (`backend/migrations/`). Chosen over hand-written SQL scripts so schema changes are versioned and reversible as the project grows.
- **pgvector**: enabled via `CREATE EXTENSION IF NOT EXISTS vector` in migration `0001_create_documents_table`. No vector column exists yet — this just makes the extension available for embeddings added later. `pgcrypto` is also enabled (provides `gen_random_uuid()` for the `documents.id` default).
- **Indexes**: `documents.category`, `documents.deadline_date`, and `documents.upload_date` are indexed (`0007_add_documents_indexes`) since every `GET /documents`/`GET /documents/deadlines` call filters or sorts on one of the three. `documents.user_id` (added in `0008_add_documents_user_id_column`) is indexed too, for the same reason — every document query now filters by it as well, see [Per-user document isolation](#per-user-document-isolation). `documents.source` (added in `0018_add_source_to_documents`) is indexed too, since `GET /documents` filters on it every call — see [Document source separation](#document-source-separation).

## API endpoints

- `GET /health` — liveness check. **Not** auth-protected (Render's health check has no way to send a token).
- `POST /auth/register` — body `{ email, name, password }`. 400s if the email is already registered or the password is under 8 characters. Hashes the password with bcrypt (`auth.hash_password()`), creates the `users` row, returns `{ access_token, token_type: "bearer" }`.
- `POST /auth/login` — body `{ email, password }`. 401s with a generic "Incorrect email or password" on either a missing user or a bad password (doesn't reveal which, to avoid leaking which emails are registered). Returns the same `{ access_token, token_type }` shape as register.
- `GET /auth/me` — requires `Authorization: Bearer <token>`. Returns the current user's `{ id, email, name, role, created_at, due_soon_threshold_days, has_signature }`. `has_signature` was added in Phase 31 (see [E-signature](#e-signature)) — a computed boolean (`User.has_signature`), never the raw signature storage path.
- `PATCH /auth/me` — requires auth. Body `{ due_soon_threshold_days }`, must be `7`/`14`/`30`/`60` (a Pydantic `Literal`, so anything else 422s automatically, not a hand-written check). Updates and returns the user, same shape as `GET /auth/me`. Deliberately separate from `PATCH /auth/profile` below — this only ever touches the one app-preference field, no current-password check needed since it's not a security-sensitive change. Backs the Settings page's **App** tab. See [Settings](#settings).
- `PATCH /auth/profile` — requires auth. Body `{ name, email }` (both required — the frontend always submits the full form, not a partial patch). 400s if `email` belongs to a different existing user (same "already registered" message as `POST /auth/register`); updating to the user's own current email is fine (excluded from the uniqueness check via `User.id != current_user.id`). Updates and returns the user, same shape as `GET /auth/me`. No current-password confirmation required, matching `PATCH /auth/me`'s reasoning — deliberately minimal for this POC (see [Authentication](#authentication)); revisit if this goes past POC, same as the token-storage tradeoff already noted there. Backs the Settings page's **Account** tab. See [Settings](#settings).
- `POST /auth/change-password` — requires auth. Body `{ current_password, new_password }`. 401s (not 400) if `current_password` doesn't match — same "wrong current password" semantics as a login failure. 400s if `new_password` is under 8 characters. 204 on success. Does **not** reissue a token — this app's JWTs aren't tied to the password hash (payload is just `{sub, exp}`) and there's no server-side revocation list, so an old token stays valid until it naturally expires either way; reissuing one here wouldn't add security, just complexity.
- `DELETE /auth/me` — requires auth. Deletes the `users` row, 204. See [Settings](#settings) for why this doesn't touch `documents` at all.
- `GET /documents` — **now requires auth**, and scoped to the current user (see [Per-user document isolation](#per-user-document-isolation)) — only returns documents that user owns. **Also always filters to `source == "upload"`** (see [Document source separation](#document-source-separation)) — a template-learning sample or a template-generated document never appears here, only in `GET /documents/templates`/`GET /documents/generated` below. Filtered server-side by optional query params: `category` (exact match against one of the 6 [categories](#categories)) and `upload_date_from` / `upload_date_to` (inclusive date range, `YYYY-MM-DD`, matched against `upload_date`). Sorting/highlighting is left to the frontend. Response model is `DocumentListOut` (`schemas.py`) — same shape as `DocumentOut` **minus `raw_text`**: the list views never read it (only the detail page does, via its own `GET /documents/{id}` fetch), and it's the dominant contributor to payload size (measured ~89% of bytes on a real 3-document response — full extracted PDF/OCR text, often 10-25KB+ per document). `extracted_json` is still included since the Documents/Tasks list rows read a few of its fields for the party-summary line (`getPartySummary()` in `frontend/.../documents/types.ts`).
- `GET /documents/deadlines` — requires auth, scoped to the current user like `GET /documents`. Returns only documents with a non-null `deadline_date`, sorted soonest-first (`ORDER BY deadline_date ASC`). **Not** filtered by `source` — see [Document source separation](#document-source-separation) for why this was deliberately left unchanged (a template-generated document with a real deadline still appears here today). Optional `urgency` query param — `overdue` (`deadline_date < today`), `due-soon` (`today <= deadline_date <= today + 30 days`), or `all`/omitted (no urgency filter, just "has a deadline"); 400s on anything else. Same `DocumentListOut` response shape as `GET /documents` (no `raw_text`, same reasoning). Registered before the `/documents/{id}/...` routes so the literal path `deadlines` is never swallowed by a path-parameter route. The `/tasks` page (`/deadlines` before Phase 27's [Navigation](#navigation) rename) calls it with no `urgency` param (fetch everything with a deadline once) and buckets the result into finer groups client-side — see the `/tasks` entry under Frontend pages.
- `GET /documents/templates` / `GET /documents/generated` — requires auth, scoped to the current user, same `DocumentListOut` shape as `GET /documents`. Return exactly the documents with `source == "template_sample"` / `source == "generated"` respectively, newest first — see [Document source separation](#document-source-separation). Power the Editing Workspace's own "Uploaded Templates"/"Generated Documents" sections instead of the main Documents list. Not cached (unlike `GET /documents`/`GET /documents/deadlines`) — small, infrequently-viewed lists scoped to one workspace panel, not worth a `TTLCache` entry. Registered before `/documents/{id}` so these literal paths are never swallowed as a `{document_id}` value, same reasoning as `/documents/deadlines`.
- `GET /documents/{id}` — requires auth. Returns a single document as the full `DocumentOut` (includes `raw_text`, unlike the list endpoints above), 404 if it doesn't exist **or belongs to a different user** (see [Per-user document isolation](#per-user-document-isolation) — same 404, not 403, either way, so a document's existence isn't leaked to a user who doesn't own it). Not filtered by `source` — a template sample or generated document is fully reachable here regardless, which is exactly how the Editing Workspace's Open button (and its "returns to the Workspace, not Documents" `?from=workspace` query param — see [Document source separation](#document-source-separation)) works. Added so `/documents/[id]` (see Frontend pages) can load standalone on a direct visit/refresh, not just from list data already in memory. Registered after `/documents/deadlines` so that literal path isn't swallowed as a `{document_id}` value.
- `POST /documents/upload` — **now requires auth.** Accepts a single file (multipart form field `file`; PDF, JPG, PNG, or TIFF, max 20MB), uploads it to the private `documents` bucket in Supabase Storage via `supabase-py` (`backend/storage.py`, authenticated with `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`), inserts a `documents` row owned by the uploading user (`filename`, `storage_path` = the bucket object key, `status="uploaded"`, `user_id` = the current user's id — see [Per-user document isolation](#per-user-document-isolation)), and **returns immediately** with that row — `{ id, status: "uploaded", category: null, raw_text: null, extracted_json: null, deadline_date: null, error_message: null }`. The extract → classify → structure pipeline (see [Document processing](#document-processing)) now runs afterward, in the background — see [Background processing](#background-processing) for why and how. Rejects unsupported extensions, empty files, and files over 20MB with a 400 before touching Storage (all still checked synchronously — only the pipeline itself was moved to the background, not file validation/upload).
- `DELETE /documents/{id}` — **now requires auth.** Deletes the `documents` row and best-effort deletes the underlying object from Supabase Storage (a storage-delete failure, e.g. the object already being gone, doesn't block removing the DB row). Returns 404 if the id doesn't exist **or isn't owned by the current user**, otherwise 204. POC-level convenience for cleaning up test uploads from the UI — no soft-delete/undo.
- `POST /documents/{id}/reprocess` — **now requires auth**, ownership-scoped like the endpoints above. Re-runs classification + structured extraction (`processing.classify_and_structure()`) against the document's **already-stored** `raw_text` — does not re-download or re-OCR the file. 400s if `raw_text` is empty (i.e. extraction itself never completed — those need a full re-upload, not this). Returns the updated row (same shape as a `GET /documents` row). This is the same logic path used by `scripts/reclassify_other_documents.py`; the dashboard's "Reprocess" button on the document detail modal calls this endpoint directly.
- `GET /documents/{id}/download-url` — requires auth, ownership-scoped. Generates a short-lived (5 minute, `DOWNLOAD_URL_EXPIRES_SECONDS` in `main.py`) Supabase Storage signed URL for the document's `storage_path` (`storage.create_signed_url()`), since the bucket is private and has no public/permanent URLs. Returns `{ url, expires_in }`. 404s if the document doesn't exist or isn't owned by the current user, 502 if Supabase Storage fails to produce a signed URL (e.g. the underlying object is gone). The URL itself is a normal `https://…supabase.co/storage/v1/object/sign/...` link — no further auth needed to fetch *that* URL, so don't log it or treat it as safe to share long-term; it expires on its own after 5 minutes regardless. Powers the "View original PDF" link on the document detail modal.
- `POST /documents/{id}/chat` — requires auth, ownership-scoped. Body `{ question }`. Sends the document's `raw_text` (truncated to the first `chat.MAX_CHARS` = 12000 characters — long documents don't send in full) plus the question to Groq (`chat.answer_question()`, same `openai/gpt-oss-120b` + `reasoning_effort="low"` + retry-with-backoff pattern as classification/structured extraction — see [GROQ_API_KEY usage](#groq_api_key-usage)) and returns `{ answer, truncated }`. `truncated` tells the caller the answer was generated from only the first part of the document, in case that matters for a long contract. 400s on an empty question or a document with no `raw_text` yet (extraction never completed — nothing to ask about); 404 if the document doesn't exist; 502 if the Groq call fails after retries. Single-turn — no conversation memory is kept server-side; the frontend's message history is purely local UI state, each question is answered independently against the same document text.
- `POST /auth/signature`, `GET /auth/signature`, `DELETE /auth/signature`, `POST /documents/{id}/sign`, `GET /documents/{id}/signed`, `GET /signed-documents/{id}/download-url` — Phase 31's self-serve e-signature endpoints (`backend/signature_router.py`). See [E-signature](#e-signature) for the full design.
- `POST /templates/learn-from-sample`, `GET /templates`, `GET /templates/{id}`, `DELETE /templates/{id}`, `POST /templates/{id}/generate` — Phase 32's document-generation-from-a-learned-template endpoints (`backend/templates_router.py`). See [Document generation](#document-generation) for the full design.

## Authentication

JWT-based, added in `backend/auth.py`. No refresh tokens, no password reset, no role-based authorization yet (`users.role` is captured but not checked anywhere) — deliberately minimal for now.

- **Passwords**: hashed with `bcrypt` directly (not `passlib`, to dodge `passlib`'s known incompatibility with `bcrypt>=4.1`). `hash_password()` / `verify_password()`.
- **Tokens**: `pyjwt`, HS256 by default, signed with `JWT_SECRET_KEY`. Payload is just `{"sub": "<user id>", "exp": ...}`. `create_access_token(subject)` issues one; `get_current_user()` (a FastAPI dependency, `Depends(get_current_user)`) decodes and verifies it, 401s on anything wrong (missing/invalid/expired token, or a `sub` that no longer matches a real user), and loads the real `User` row from the DB for the request to use.
- **Sending the token**: standard `Authorization: Bearer <token>` header. `auth.py` uses FastAPI's `OAuth2PasswordBearer(tokenUrl="auth/login")` purely to extract that header (and to make `/docs`'s "Authorize" button work) — `/auth/login` itself takes a plain JSON body, not OAuth2's form-encoded `username`/`password`.
- **What's protected**: every `/documents/*` endpoint now requires a valid token via `Depends(get_current_user)`. `/health` is intentionally left open (Render's health checker has no token to send).

**Frontend wiring** (`frontend/lib/auth-context.tsx`, an `AuthProvider` mounted in the root layout so it's available on every route including `/login`/`/register`):

- **Token storage: `localStorage`, not an httpOnly cookie** — deliberate for this POC. An httpOnly cookie would need the backend to set it and the frontend to send it cross-origin (different ports locally, different domains once deployed to Render), which means CORS with `allow_credentials=True` and dealing with `SameSite` for cross-site requests. Storing the token and attaching it manually via an `Authorization` header sidesteps all of that. Trade-off: readable by any JS on the page (XSS risk), unlike an httpOnly cookie — revisit if this goes past POC. This is exactly why the CORS origin allowlist in [Security](#security) matters even though the app doesn't use cookies: a `localStorage` token is only as safe as the set of origins allowed to run JS that can reach the API on the user's behalf. **Re-assessed, not changed, in the [Security audit](#security-audit)**: real confidential data now flowing through the app raises the stakes of this trade-off, but a full httpOnly-cookie migration was judged too invasive to fold into that audit — it's an open recommendation there, still exactly this same trade-off in the meantime.
- `AuthProvider` checks `localStorage` on mount and, if a token is there, calls `GET /auth/me` to validate it and load the real user; an invalid/expired token is cleared silently (back to logged-out) rather than erroring.
- `login()`/`register()` call the respective endpoint, then immediately call `GET /auth/me` with the new token before storing anything, so `user` is never set from an unverified token.
- `authFetch(path, init)` is the one place that attaches `Authorization: Bearer <token>` and handles a `401` response by clearing the token and redirecting to `/login` (session-expired handling) — every page under `(app)/` (`/home`, `/documents`, `/tasks`, `/documents/[id]`, `/workspace`, `/analytics`, `/settings`) uses this instead of raw `fetch` for anything hitting the backend. `upload/page.tsx` uses `XMLHttpRequest` (for upload progress), which can't go through `authFetch`, so it reads `token` from the context directly and calls `xhr.setRequestHeader("Authorization", ...)` itself, with the same 401-triggers-logout handling done manually in `xhr.onload`.
- `refreshUser()` re-fetches `GET /auth/me` and replaces `user` in context state — used after a Settings-page change (e.g. `due_soon_threshold_days`) so every consumer of `user` (stat tile labels, urgency thresholds, the sidebar) updates without a full page reload.
- **Route protection**: `components/auth-guard.tsx`'s `AuthGuard` wraps the `(app)` route group's `layout.tsx` (so it covers `/home`, `/documents`, `/tasks`, `/upload`, `/documents/[id]`, `/workspace`, `/analytics`, `/settings` — everything with the sidebar, as one block rather than a named per-route list — see [Navigation](#navigation)). While `loading` (checking the stored token) or if there's no `user`, it renders a bare "Loading..." state and `router.replace("/login")`s once loading settles with no user; it only renders `children` once a real user is confirmed. `/login` and `/register` sit outside the `(app)` group, so they're never gated, and each redirects **to** `/home` (Home — was `/` until the public landing page took over the root route, see [Public landing page](#public-landing-page); was `/dashboard` before that, per Phase 27's [Navigation](#navigation) rename) on mount if a user is already logged in (so a logged-in user hitting `/login` doesn't see the form again). The public landing page at `/` is itself outside the `(app)` group too (top-level `app/page.tsx`) and is never auth-gated — it's meant to be visible to a logged-out visitor.
- **Sidebar** (`components/sidebar.tsx`): the bottom avatar/name/email come from the real `user` object (`getInitials()` derives the two-letter avatar from `user.name`), and the whole avatar/name/email chip is now a `<Link href="/settings">` (previously just static display) — clicking it, not just the separate "Settings" nav item above, opens Settings, matching the common GitHub/Linear pattern of your own account chip being a settings entry point. The logout button (`LogOut` icon, a sibling `<button>` next to the link, not nested inside it) stays its own separate click target. Nav is the 6-item map from Phase 27's [Navigation](#navigation) section (`Home` / `Editing Workspace` / `Documents` / `Tasks` / `Analytics` / `Settings`) — all real routes, nothing disabled/"Soon" left in the sidebar.
- `/register` (`app/register/page.tsx`) is a new page, visually identical to `/login` (same split-screen scaffold) — form fields are `name`/`email`/`password` (backend's exact `UserCreate` shape), calls `register()`, redirects to `/home` (Home) on success. The two pages cross-link ("Create an account" / "Log in").

## Security

Hardening pass over the backend for a real (non-POC-only) deployment. Each item below was verified live, not just read from the code.

- **CORS**: `allow_origins=["*"]` replaced with an explicit allowlist read from `ALLOWED_ORIGINS` (`config.py`, comma-separated, defaults to `http://localhost:3000`) — see [Environment variables](#environment-variables). `main.py` passes this straight to `CORSMiddleware`. Set `ALLOWED_ORIGINS` in the Render dashboard to the real deployed frontend URL(s) — `render.yaml` declares it with `sync: false` like the other secrets. **Currently must list two origins, not one** — see [Second frontend deployment (Vercel)](#second-frontend-deployment-vercel): both `https://documentos-ai-frontend.onrender.com` and `https://document-os-ai.vercel.app` are live and calling this same backend. Verified live: a preflight `OPTIONS` request from `http://localhost:3000` gets back `access-control-allow-origin: http://localhost:3000`; the same request from `http://evil.com` gets a 400 with no CORS header at all. `allow_credentials` is intentionally left unset (`False`) — the app doesn't use cookies (see the `localStorage`-token note under [Authentication](#authentication)), so there's nothing that needs it.
- **File upload content validation**: `file_validation.py`'s `matches_declared_type()` checks the first few bytes of an uploaded file against known magic-byte signatures for PDF (`%PDF-`), JPEG (`FF D8 FF`), PNG (the 8-byte PNG signature), and TIFF (`II*\0`/`MM\0*` byte-order marks), called from `POST /documents/upload` right after the existing extension/size checks. This closes the gap where the old code trusted the filename's extension alone — trivially spoofable by renaming any file to `.pdf`. A mismatch (e.g. a `.txt` file renamed to `.pdf`) gets a 400 before the file ever reaches Supabase Storage or the extraction pipeline. Deliberately hand-rolled rather than adding `python-magic` (needs the system `libmagic` library — another Dockerfile/Windows-install dependency alongside Tesseract, for a check that only needs to distinguish 4 known formats). Verified live: a plain-text file renamed to `fake.pdf` is rejected with `"File content doesn't match its extension..."`; a genuine (if minimal) PDF uploads and processes normally.
- **Password complexity**: `auth.validate_password_strength()` (used by both `POST /auth/register` and `POST /auth/change-password`, replacing what used to be two separately hand-written `len(password) < 8` checks) now requires, beyond the existing 8-character minimum, at least one letter and one number — enough to reject trivially-guessable all-digit (`12345678`) or all-letter (`password`) values without a symbol/uppercase rule that mostly just annoys users for a POC-scale app. Verified live against all four cases (all-digit, all-letter, too-short, valid) — each gets the specific, correct error message.
- **JWT expiry / refresh tokens**: checked `JWT_EXPIRES_MINUTES` (`config.py`) — it defaults to `1440` minutes (24 hours), which is a reasonable session length, not "very short." A refresh-token flow was **not** added: it solves a problem (users logged out mid-session because of a short-lived token) that this app doesn't have. Adding one now would mean a new token type, a new endpoint, and rotation/revocation logic for no real gain — worth revisiting only if `JWT_EXPIRES_MINUTES` is ever deliberately lowered (e.g. for a stricter security posture) to the point where 24-hour sessions are no longer acceptable. **Partially revisited in the [Security audit](#security-audit)**: a stolen token still rode out its full 24h lifetime even after a user changed their password in response — `users.token_version` now closes that one specific case (see the Security audit section for the mechanism). A general "log out all other sessions" button and true short-lived-refresh-token rotation are still open recommendations there, not full replacements for this note.
- **No secrets in logs or API responses**: audited every `except Exception` in the backend. The one real leak risk was `processing.py`, which stored `str(exc)` directly into `documents.error_message` — a field returned by `GET /documents`/`GET /documents/{id}`. At the time this was fixed, that was visible to **any** authenticated user, not just the uploader — [Per-user document isolation](#per-user-document-isolation) has since closed that specific exposure too, but the sanitization below is still the right call regardless of who can see the field: a Storage/Groq/DB client's exception text is generally just an API error message, not a raw credential, but there's no reason to take that on faith. Fixed: `processing.py` now logs the full exception server-side via `logger.exception(...)` (visible in local console / Render logs) and stores one of three fixed, generic strings (`EXTRACTION_FAILED_MESSAGE`/`CLASSIFICATION_FAILED_MESSAGE`/`STRUCTURING_FAILED_MESSAGE`) as `error_message` — never the exception's own text. `main.py`'s other broad `except Exception` blocks (`chat`, `download-url`, the best-effort storage delete) already returned generic messages to the client; added `logger.exception`/`logger.warning` calls there too so failures are still debuggable server-side instead of silently swallowed. `main.py` now calls `logging.basicConfig(...)` once at import time so all of this actually gets written somewhere. Verified with a direct unit-level test: a mocked exception whose message contained a fake secret never appeared in `document.error_message` — only the sanitized fallback string did.

## Rate limiting

Added via `slowapi` (`backend/rate_limit.py`) to prevent credential-stuffing against `/auth/login` and to protect the app's Groq quota from being exhausted by repeated uploads (both hardening items are decorator-based, not global middleware — see below for why that's enough here).

- **`POST /auth/login`**: `5/minute`, keyed by client IP (slowapi's default `get_remote_address`). Verified live: 5 requests in a minute succeed (each returning a normal 401 for a wrong password), the 6th+ get a 429.
- **`POST /documents/upload`**: `20/hour`, keyed **per authenticated user** (`rate_limit.user_or_ip_key`) instead of per-IP — otherwise an office/NAT sharing one public IP would share a single upload quota. The key function decodes the JWT straight from the `Authorization` header (independent of the `get_current_user` dependency, since slowapi's `key_func` only ever receives the raw `Request`); falls back to per-IP for a missing/invalid token, which 401s from the real auth dependency regardless. Each upload triggers 2-3 Groq calls (classify + structure, see [Document processing](#document-processing)), and Groq's free tier is itself rate-limited to ~30 requests/minute (see [Known free-tier limits](#known-free-tier-limits-to-watch)) — 20 uploads/hour per user keeps any single user's worst case well under that.
- **429 response shape**: `rate_limit.rate_limit_exceeded_handler` (registered via `app.add_exception_handler(RateLimitExceeded, ...)`) returns `{"detail": "Too many requests. Please wait a moment and try again."}` — deliberately matching the `{"detail": ...}` shape every other error response in this app uses (see `parseErrorDetail` in `auth-context.tsx`), instead of slowapi's own default `{"error": ...}` shape. Both `X-RateLimit-*` and `Retry-After` headers are included (`headers_enabled=True` on the `Limiter`); a `response: Response` parameter had to be added to both decorated endpoint signatures (`login`, `upload_document`) for slowapi to be able to inject those headers on a normal (non-429) response too — without it, slowapi raises internally trying to inject headers into `None`, which surfaced as a real 500 during testing before this fix. Verified live: hitting the request 6 times in a minute against `/auth/login` gets 401/401/401/429/429/429/429; the response body on the 429s is exactly the shared `{"detail": ...}` shape.
- **Frontend**: no changes were needed. Because the 429 body already matches this app's standard `{"detail": ...}` error shape, the existing error-handling paths pick it up automatically — `login()`/`register()` in `auth-context.tsx` already throw `new Error(parseErrorDetail(res, ...))` and display `err.message` on the page, and `upload/page.tsx`'s `XMLHttpRequest.onload` already falls into its existing `setMessage(data.detail ?? "Upload failed.")` branch for any non-2xx/non-401 status. Verified: both surfaces show the real rate-limit message, not a generic "Login failed."/"Upload failed." fallback.
- **Storage**: in-memory (`slowapi`'s default via the `limits` library) — fine for this app's single-process deployment (`uvicorn` is run with no `--workers`, both locally — see [Running locally](#running-locally) — and on Render, per `render.yaml`); counters reset on a restart/redeploy, which is an acceptable tradeoff at this scale rather than standing up Redis for a POC.
- **Every `/tools/*` endpoint**: same `20/hour` per-user shape as `/documents/upload` (same `rate_limit.user_or_ip_key`) — see [Document tools](#document-tools). These are at least as compute-heavy per call (Ghostscript/LibreOffice/OCR subprocesses can each run for several seconds to tens of seconds), so reusing the upload endpoint's budget is, if anything, conservative rather than an arbitrary new number. Verified live: 22 rapid `POST /tools/convert-image` calls from the same user got 200s until the limit, then 429s, with the same shared `{"detail": ...}` shape.
- **`POST /editor/chat`**: same `20/hour` shape again — see [Editor assistant](#editor-assistant). One chat turn can trigger several chained tool calls plus multiple Groq round trips, so if anything this is more conservative than the direct endpoints' own justification for the same number.
- **`POST /copilot/chat`**: same `20/hour` shape once more — see [Copilot](#copilot). Same reasoning: a single turn can mean several Groq round trips against real document data.
- **`POST /analytics/generate`**: same `20/hour` shape again — see [Analytics](#analytics). Mitigated further by its own 10-minute cache (longer than any other cache in this app — see [Caching](#caching)), so in practice a user hits this rate limit only by mashing "Regenerate," not from normal page visits.
- **`POST /documents/{id}/sign`**: same `20/hour` shape once more — see [E-signature](#e-signature). Signing shells out to PyMuPDF, not free, so the same shared per-user budget applies rather than a new number. **`POST /auth/signature` (saving a signature image) now shares this same limit too** — a [Security audit](#security-audit) finding flagged it as the one upload endpoint in the app without one (originally left unlimited on the reasoning that it's a rare, one-off Settings action, not a repeatable-abuse surface like signing/Groq calls — but "unlike every other upload endpoint" won out as the more important consistency argument once actually audited).
- **Every `/documents/{id}/chat` and `/documents/{id}/reprocess` call**: same `20/hour` shape — added as a [Security audit](#security-audit) fix. Both are real Groq-calling endpoints (chat answers a question against the document's `raw_text`; reprocess re-runs classify+structure) that had shipped with **no rate limit at all** since their original phases — the audit is what caught this, not an original design decision.
- **`POST /templates/learn-from-sample`** and **`POST /templates/{id}/generate`**: same `20/hour` shape again — see [Document generation](#document-generation). Both call Groq (schema learning and, for the natural-language path, instruction parsing), same reasoning as every other AI-calling endpoint sharing this budget.

## Settings

`/settings` (`app/(app)/settings/page.tsx`) — reachable both from the sidebar nav's "Settings" item and, now, by clicking the account chip (avatar/name/email) at the bottom of the sidebar itself — see [Design system](#design-system)'s Layout note. Split into two tabs (a simple button-group toggle, `SettingsTab` state, no routing/URL involved — matching the GitHub/Linear "Account" vs. "Workspace/App" settings split), each backed by real endpoints, no inert placeholders:

- **Account tab** (default) — everything about the person's own identity/credentials:
  - **Profile** — `name`/`email`, now genuinely editable (previously read-only — there was no `PATCH` for these until this phase). Submits both fields together to `PATCH /auth/profile`, then `refreshUser()` — which is why the sidebar's own name/email update immediately after a save, since the sidebar reads the same `user` object from `AuthProvider`.
  - **Signature** (Phase 31 — see [E-signature](#e-signature)) — draw a signature on a canvas or upload a PNG/JPEG, then "Save signature" (`POST /auth/signature`). Shows the currently saved signature (`GET /auth/signature`, fetched fresh on mount) with a "Remove signature" button (`DELETE /auth/signature`). Only one signature is ever saved per user — a new save replaces the old one, it isn't a history.
  - **Change password** — unchanged from before this phase: `current_password`/`new_password`/`confirm_new_password` with a client-side match check, submits to `POST /auth/change-password`.
  - **Danger zone** — unchanged: "Delete account" needs the user's own email typed exactly (case-insensitive) to enable the button — the typed-email gate **is** the confirmation step, no extra native `confirm()` dialog. Calls `DELETE /auth/me` then `logout()`.
- **App tab** — app-wide preferences, not identity: currently just "Due soon threshold" (a 4-way button group, 7/14/30/60 days, current value highlighted from `user.due_soon_threshold_days`). Clicking a different value calls `PATCH /auth/me`, then `refreshUser()`. This is the value that now actually drives every "due soon"/urgency computation in the app — see below. Anything else app-wide (not identity-related) added later belongs on this tab, next to it.

**Where the "due soon" threshold actually propagates**: `getDeadlineUrgency()`, `formatRelativeDeadline()`, and `getDeadlineBucket()` (all in `documents/types.ts`, moved from `dashboard/types.ts` in Phase 27's [Navigation](#navigation) rename) each take an optional `thresholdDays` parameter (defaulting to `DEFAULT_DUE_SOON_THRESHOLD_DAYS = 30` for any caller that doesn't have the real value in scope yet). Every real call site — the Documents page's stat tiles and `DocumentsTable`, Home's own stat tiles and "nearest upcoming deadlines" list, the `/tasks` page's bucketing, and the document detail page's urgency badge — reads `user?.due_soon_threshold_days ?? DEFAULT_DUE_SOON_THRESHOLD_DAYS` and passes it through explicitly; nothing hardcodes `30` anymore except that one shared fallback constant. On `/tasks`, the "due this week" sub-bucket stays a fixed 7 days regardless of the threshold (it's a finer subdivision, not what the Settings control is about); the second bucket's label was changed from "Due this month" to "Due soon" since "month" stops being accurate once the threshold is configurable (e.g. 60 days, or 7 days collapsing that bucket to empty). The backend's own `GET /documents/deadlines?urgency=due-soon` filter still hardcodes 30 days server-side — that query param isn't called by any current frontend page (the `/tasks` page fetches everything with a deadline and buckets client-side using the real per-user threshold instead), so it was left as a generic default rather than threaded through as a query param nobody sends yet.

**Account deletion now cascades to owned documents**: `documents.user_id` exists (see [Per-user document isolation](#per-user-document-isolation)), so `DELETE /auth/me` has a real relationship to act on. `delete_account()` deletes every document the user owns — best-effort Storage cleanup per document (same pattern as `DELETE /documents/{id}`), then the DB rows, then the `users` row — rather than relying only on the FK's `ON DELETE CASCADE`, which would silently skip the Storage cleanup and leave orphaned objects in the bucket. This replaces the earlier behavior (documented here until this phase), where account deletion touched only the `users` row because there was no ownership relationship to cascade through at all. Phase 31 extended this the same way for `signed_documents` and the user's own signature image — see [E-signature](#e-signature) for why that one specifically needed explicit cleanup (no retention sweep to eventually catch it otherwise).

## Document processing

`backend/processing.py: process_document()` runs after every upload, as a **background task** (see [Background processing](#background-processing)) rather than inline in the upload request:

1. **Extraction** — downloads the file from Supabase Storage via `storage.download_file_from_storage()`, keyed by the document's stored `storage_path`, then `backend/extraction.py: extract_text()`: for PDFs, tries PyMuPDF's (`fitz`) embedded text layer first; if that yields fewer than 20 characters (i.e. no real text layer, likely a scanned PDF), it rasterizes each page and runs Tesseract OCR (`pytesseract`) instead. For JPG/PNG/TIFF, it goes straight to Tesseract OCR.
   - On success: `raw_text` is saved and `status` is set to `extracted`, then classification runs (step 2) immediately.
   - On any exception (Storage download failure, corrupt file, OCR error, etc.): `status` is set to `extraction_failed`, the exception message is stored in `error_message`, and the pipeline stops.
2. **Classification** — `backend/classification.py: classify_text()` sends the first 4000 characters of `raw_text` to Groq (see [GROQ_API_KEY usage](#groq_api_key-usage) below) with `response_format={"type": "json_object"}`, asking for `{"category": ..., "reasoning": ...}` picking exactly one of the 6 [categories](#categories) below. `parse_classification()` matches the returned `category` against the known list (exact match, then substring fallback), falling back to `Other` if the response is unparseable or doesn't match anything — but `reasoning` is always kept (synthesizing a fallback string like `"The classifier's response could not be parsed: ..."` if the model didn't provide one), so an `Other` classification is never a dead end with no explanation.
   - On success: `category` and `classification_reasoning` are saved, `classification_version` is stamped with `classification.CURRENT_CLASSIFICATION_VERSION`, `status` is set to `classified`, then structured extraction (step 3) runs immediately.
   - On any exception (including exhausted retries — see below): `status` is set to `classification_failed`, `error_message` is set, `raw_text` from step 1 is kept, and the pipeline stops.
3. **Structured extraction** — `backend/structured_extraction.py: extract_structured_data()`. Skipped entirely for `Bank Statement` and `Other` (they go straight to `status = "processed"` with `extracted_json` left `null`). For the other four [categories](#categories), sends the first 4000 characters of `raw_text` to Groq with a category-specific system prompt listing the exact JSON schema to return (using Groq's `response_format={"type": "json_object"}`), then `json.loads()`s the response — see [Categories](#categories) for the exact field list and `deadline_date` mapping per category.
   - If the first response fails to parse as JSON, it retries once with a stricter prompt (explicitly telling the model its previous reply wasn't valid JSON). If that also fails, `extracted_json` is set to `{"parse_error": true, "raw_response": "<the unparsed text>"}` and `deadline_date` stays `null` — this still counts as a completed step (`status = "processed"`), not a failure, since a bad LLM response isn't retried indefinitely.
   - On success (parsed or fallback): `extracted_json`/`deadline_date` are saved and `status` is set to `processed`.
   - On any other exception (e.g. Groq API error after exhausted retries): `status` is set to `structuring_failed` and `error_message` is set; `category`/`raw_text` from earlier steps are kept.

## Categories

Seven recognized categories (`classification.CATEGORIES`, mirrored in `frontend/app/(app)/documents/types.ts`'s `CATEGORIES`): `Agreement`, `Invoice`, `GST Document`, `GST Filing`, `Bank Statement`, `Purchase Order`, `Other`. `GST Filing` was added in Phase 30 (see [India-specific document intelligence](#india-specific-document-intelligence) below) as a periodic-return-specific sibling of the older, more generic `GST Document`. `Bank Statement` and `Other` have no structured-extraction schema (see step 3 above); the other five do:

| Category | Extracted fields | `deadline_date` source |
|---|---|---|
| Agreement | `party_names`, `effective_date`, `expiry_date`, `auto_renewal`, `renewal_notice_period`, `termination_clause_summary`, `key_obligations`, `penalty_clauses` | `expiry_date` |
| Invoice | `vendor_name`, `invoice_number`, `invoice_date`, `due_date`, `gst_number`, `line_items`, `subtotal`, `tax_breakdown`, `amount` | `due_date` |
| GST Document | `gstin`, `period`, `tax_amount`, `filing_date` | `filing_date` |
| GST Filing | `gstin`, `return_type`, `period`, `filing_date`, `arn`, `cgst_amount`, `sgst_amount`, `igst_amount`, `tax_liability`, `late_fee` | `filing_date` |
| Purchase Order | `po_number`, `vendor`, `buyer`, `delivery_date`, `line_items`, `subtotal`, `tax_breakdown`, `total_amount` | `delivery_date` |

Every category above also gets whatever India-specific additions apply to it — see the next section for the full field list, the region-detection mechanism, and how validation/derivation works.

**Line items** (Invoice/Purchase Order only, added because the original single `item_summary` string flattened real itemized documents into an unusable blob): `line_items` is an array, one object per row in the document's items table — `{description, hsn_sac_code, quantity, unit, rate, tax_percent, amount}`, all nullable except `description`. The prompt (`structured_extraction._build_messages()`) explicitly instructs the model to go row by row and extract every line item separately rather than summarizing or merging rows — worth re-checking if a document comes back with suspiciously few items for how many rows it visibly has. `tax_breakdown` is a smaller array in the same style — `{label, rate_percent, amount}` — for tax lines shown separately from the items table (e.g. CGST/SGST/IGST), alongside a plain `subtotal` number. No DB migration was needed for any of this: `extracted_json` is `JSONB` (Postgres has no issue with nested arrays) and the Pydantic schema types it as `Any` — nothing in the pipeline (`processing.py`, `schemas.py`, `main.py`) inspects or reshapes the dict's contents, it's a straight pass-through end to end, so arbitrarily nested arrays were already fully supported without any code change. `max_tokens` for structured extraction was raised from 800 to 2000 (`structured_extraction._call_groq()`) since a multi-row `line_items` array is a meaningfully larger JSON response than the old flat schema, and this app has twice already been bitten by `max_tokens` being too tight for this reasoning model's `reasoning` + `content` split (see the gotcha below). Verified against the two real documents already in the DB: reprocessing the KGRAPH invoice and the OAM purchase order both returned correct `line_items`/`tax_breakdown`/`subtotal` with dollar/rupee figures matching the source text exactly (e.g. the PO's `tax_breakdown` IGST amount and `total_amount` matched the document's own "Amount in words" line) — though not flawlessly: on messy PDF-extracted raw text where the items table's column structure is lost, the model can still mis-map ambiguous numbers to the wrong field (e.g. `rate` vs `quantity`) or leave `rate` null when it's only derivable by back-computing from `quantity`/`amount`. That's a text-extraction/LLM-interpretation limit, not a schema or code bug — real invoice text just doesn't always arrive with unambiguous column boundaries.

**Adding a new category** (e.g. an 8th one later) means updating, in lockstep: `classification.CATEGORIES` (+ bump `CURRENT_CLASSIFICATION_VERSION`), `structured_extraction.SCHEMAS`/`DEADLINE_FIELD` if it needs structured extraction, `processing.STRUCTURED_CATEGORIES` if so, and on the frontend `types.ts`'s `CATEGORIES`/`CATEGORY_ICONS`/`FIELD_LABELS`/`FIELD_SECTIONS`/`CURRENT_CLASSIFICATION_VERSION` (the last one must match the backend exactly, by hand — it's duplicated, not shared, same as `CATEGORIES` itself already was). Also check `copilot_chat.py` — it now imports `CATEGORIES` from `classification.py` rather than keeping its own copy (a duplicate list was found and fixed in Phase 30), so it updates for free, but it's worth confirming nothing else in the backend has grown a fresh hardcoded copy since. `GST Filing` (Phase 30) is the category that most recently went through this whole list.

**Why `classification_version` exists**: before Purchase Order was added, real Purchase Order documents were landing on `Other` — not a bug, just a category gap. Bumping `CURRENT_CLASSIFICATION_VERSION` whenever the category list changes, and stamping every classified document with the version it was classified under, lets the app tell "deliberately `Other` under today's full list" apart from "`Other` because the right category didn't exist yet" — only the latter gets the "may be misclassified, try reprocessing" suggestion (`isStaleOtherClassification()` in `app/(app)/documents/[id]/page.tsx`; `*_failed` documents still always get that suggestion regardless of version, unaffected by this). Verified end-to-end against a real document that was stuck at `category="Other"`/`classification_version=1`: reprocessing it correctly produced `category="Purchase Order"`, `classification_version=2`, and accurate extracted fields (PO number, amount, delivery date all matched the source document).

Each step stores failures in `status`/`error_message` rather than raising, so `GET /documents` always reflects the real outcome instead of the request crashing.

## India-specific document intelligence

Phase 30. Deepens extraction/validation specifically for Indian compliance documents (GSTIN/PAN, CGST/SGST/IGST, lakh/crore amounts) — deliberately **additive**, not a schema replacement: a UK/US/generic document's schema, prompt, and output JSON shape are all byte-for-byte identical to what they were before this phase. All of the logic below lives in `backend/india_validation.py` (new module) plus additions to `backend/structured_extraction.py`; nothing here is asked of the LLM when it can instead be computed deterministically in Python — same "don't trust the model with arithmetic" philosophy as [Analytics](#analytics)'s traceability enforcement.

**Region detection — deterministic, not a second Groq call.** `india_validation.detect_region(raw_text)` returns `"IN"` or `"generic"` by regex/keyword scan of the document's **full** `raw_text` (not the 4000-char truncated extraction window) — a real GSTIN- or PAN-shaped match is enough on its own; otherwise it falls back to requiring 2+ hits among `GSTIN`/`CGST`/`SGST`/`IGST`/`HSN`/`SAC`/₹/`Rs.`/lakh/crore, so one coincidental PAN-shaped substring can't alone flip a genuinely generic document. `structured_extraction.extract_structured_data()` calls this once per extraction and threads the result through `_build_messages()`: only when region is `"IN"` does the prompt gain the category's `INDIA_EXTRA_FIELDS` (see below) and a short note about Indian digit-grouping/lakh/crore amounts — a generic document's prompt and schema are otherwise exactly what they were pre-Phase-30. `"GST Filing"` (see below) always uses region `"IN"` unconditionally, since that category is inherently India-specific by definition regardless of what a truncated/thin raw-text scan would say.

**New fields, by category** (all in `structured_extraction.INDIA_EXTRA_FIELDS`, merged into the base schema only when region is `"IN"`):

| Category | New LLM-extracted fields (region-gated) |
|---|---|
| Invoice | `pan`, `place_of_supply`, `tds_amount`, `tcs_amount` |
| Purchase Order | `vendor_gstin`, `buyer_gstin`, `place_of_supply` |
| Agreement | `party_pan`, `party_gstin`, `stamp_duty` |

`GST Document`'s existing `gstin` field and Invoice's existing `gst_number` field needed no schema change — they already existed pre-Phase-30 and just gained validation (below).

**CGST/SGST/IGST split and `tax_type` — derived deterministically, not re-extracted.** Rather than asking the model to redundantly extract `cgst_amount`/`sgst_amount`/`igst_amount` as parallel fields alongside the existing `tax_breakdown` array (risking the two disagreeing), `structured_extraction._derive_gst_split_from_tax_breakdown()` scans the already-extracted `tax_breakdown` entries (Invoice/Purchase Order only) by label — matching `cgst`/`sgst`/`igst` as a **leading**, not trailing, word-boundary (`\bigst`, not `\bigst\b`), because a real uploaded invoice's tax line is literally labelled `"IGST18"` with no separator before the rate, which a trailing `\b` would never match — and sums matching entries into `cgst_amount`/`sgst_amount`/`igst_amount` on the top-level dict, only when at least one matching entry exists (so a generic invoice's `tax_breakdown` — e.g. a UK "VAT" line — derives nothing, adding zero new keys). `_derive_tax_type()` then sets `tax_type` to `"intra_state"` (CGST/SGST present), `"inter_state"` (IGST present), or `"mixed"` (both) — for Invoice/Purchase Order (from the derived split above) and for `GST Filing` (from its own directly-extracted `cgst_amount`/`sgst_amount`/`igst_amount` fields, since a return filing has no line-itemized `tax_breakdown` to derive from).

**GSTIN/PAN validation — real, not just extraction.** `india_validation.validate_gstin()` checks both the 15-character structure (2-digit state code + 10-char PAN + 1-char entity code + literal `Z` + 1-char checksum) **and** the checksum digit itself, using the real ISO-7064-MOD-37-36-family algorithm (36-character alphabet `0-9A-Z`, alternating ×1/×2 position weights, quotient+remainder-mod-36 summed over the first 14 characters). `validate_pan()` is structural only (5 letters + 4 digits + 1 letter) — PAN has no public checksum digit, unlike GSTIN, which embeds a PAN internally. `structured_extraction._apply_identifier_validation()` runs unconditionally after every extraction (not region-gated — these fields either already existed pre-Phase-30 or are simply absent on a generic document) and adds a `<field>_valid` boolean sibling key (`gst_number_valid`, `gstin_valid`, `pan_valid`, `party_pan_valid`, `party_gstin_valid`, `vendor_gstin_valid`, `buyer_gstin_valid`) wherever the corresponding identifier field is actually a non-empty string — never added at all when the field is null, so a non-Indian document gains zero new keys.

*The checksum algorithm was verified, not assumed*, before being trusted: cross-checked against a real, independently-published GSTIN (`33AAACC1206D1ZN`, Central Warehousing Corporation) via two different public sources, then verified against the two real vendor/buyer GSTINs already present in this app's own live documents (`29AAKCK4469L1ZQ`, `27AAACO8897J1ZO`) — both passed. `backend/tests/test_india_validation.py` encodes all three as regression fixtures, plus a deliberately-tampered checksum (rejected) and structural-malformation cases (rejected).

**Indian numeric formatting — parsed, not just hoped for.** `india_validation.parse_indian_number()` converts either digit form (`₹5,40,000`, `Rs. 5,40,000.50`, plain Indian comma-grouped digits — comma position doesn't matter once stripped, `float()` handles the ungrouped digits fine) or word form (`"five lakh forty thousand"`, `"Rupees Five Lakh Forty Thousand Only"` — filler words `rupees`/`only`/`and`/`inr` stripped, `lakh`/`crore` treated as scale words exactly like `thousand` in a standard word-to-number parser) into a clean `float`. `structured_extraction._coerce_numeric_strings()` applies this as a belt-and-suspenders pass (on top of a prompt instruction to convert these itself) over every schema field typed `"number"` plus `line_items`/`tax_breakdown` sub-fields, **only** when the model returned a string where a number was expected — if the model already returned a clean number (the common case — see verification below), nothing is touched.

**HSN/SAC codes**: already a proper field (`line_items[].hsn_sac_code`) since before this phase — confirmed still populating correctly on reprocessing, not something this phase needed to add.

## Document tools

Phase 21. A separate set of file-transformation endpoints — merge/split/compress PDF, PDF↔DOCX, image convert/resize, OCR-to-searchable-PDF. Deliberately **not** part of the document-intelligence pipeline above: no classification, no structured-field extraction, no Groq call at all. These are pure utility operations, closer to "an iLovePDF/Smallpdf clone" than to the `documents` registry.

**Design decision — direct multipart upload per call, not a separate upload-then-process step.** Each endpoint takes its input file(s) directly as a multipart body and returns the transformed output's metadata in one round trip, the same shape as `POST /documents/upload` already uses. A decoupled "upload a working file, then reference it by id in a second call" flow was considered and rejected: every one of these operations is a single-shot, stateless transformation (nothing here is ever reprocessed or revisited the way a `documents` row is), so a second upload step would only add a route and a wait with no real benefit.

**Endpoints** (`backend/tools_router.py`, mounted at `/tools/*`; all require auth via `Depends(get_current_user)`, are scoped to the calling user, and share the `20/hour` per-user rate limit — see [Rate limiting](#rate-limiting)):

| Endpoint | Input | Output |
|---|---|---|
| `POST /tools/merge-pdf` | `files`: 2+ PDFs (multipart) | one merged PDF |
| `POST /tools/split-pdf` | `file`: one PDF, optional `ranges` form field (e.g. `"1-3,5,7-9"`; omitted = one PDF per page) | a JSON array of output files, one per page/range |
| `POST /tools/compress-pdf` | `file`: one PDF, `quality`: `low`/`medium`/`high` (form field, default `medium`) | a recompressed PDF |
| `POST /tools/pdf-to-docx` | `file`: one PDF | a `.docx` |
| `POST /tools/docx-to-pdf` | `file`: one `.docx` | a `.pdf` |
| `POST /tools/convert-image` | `file`: JPG/PNG/TIFF, `target_format`: `jpg`/`png`/`tiff` (form field) | the converted image |
| `POST /tools/resize-image` | `file`: JPG/PNG/TIFF, at least one of `width`/`height`/`target_size_kb` (form fields) | the resized image |
| `POST /tools/ocr-pdf` | `file`: one PDF, optional `force_ocr` (form field, default `false`) | the same PDF with an invisible OCR text layer added |
| `GET /tools/{id}/download-url` | — | `{url, expires_in}` — a 300s Supabase Storage signed URL, same pattern as `GET /documents/{id}/download-url` |

Every transform endpoint returns a `ToolFileOut` (`{id, tool_name, original_filename, output_filename, mime_type, size_bytes, created_at, expires_at}`) — the actual file bytes are never inlined in the JSON response; the client fetches them via the `download-url` endpoint, same as the main documents pipeline. `split-pdf` is the one exception that returns a JSON **array** of `ToolFileOut` (one row per output file) instead of a single object, since it's the only tool that can produce more than one output file per call.

**Libraries and why**:

- **pikepdf** (`backend/pdf_tools.py`) — merge/split. A pure-Python-facing wrapper around `qpdf` (statically linked into the wheel, no separate system install), so page-level operations (`Pdf.pages.extend(...)`, slicing) are cheap and don't shell out to anything.
- **Ghostscript**, invoked directly via `subprocess` (`backend/pdf_tools.py: compress_pdf()`) — recompresses through the `pdfwrite` device at one of three `-dPDFSETTINGS` presets (`/screen`, `/ebook`, `/printer` for `low`/`medium`/`high`), which mainly controls the DPI embedded images get downsampled to. Chosen over a pure-Python approach because there isn't a good one — real PDF compression gains come from re-encoding embedded images and font subsetting, which is exactly what Ghostscript's `pdfwrite` device already does well.
- **pdf2docx** (`backend/pdf_tools.py: pdf_to_docx()`) — layout-aware PDF→DOCX (paragraphs, tables), built on PyMuPDF (already a dependency via `extraction.py`) — no extra system binary.
- **LibreOffice headless** (`backend/office_tools.py: docx_to_pdf()`) — chosen over `docx2pdf` specifically because `docx2pdf` shells out to MS Word via Windows COM automation and only works on Windows with Word installed, a non-starter on Render's Linux container. `soffice --headless --convert-to pdf` works cross-platform with no Word license. Each call passes `-env:UserInstallation=<a fresh temp dir>` to give itself an isolated LibreOffice profile — without this, concurrent headless conversions sharing the default profile can collide on its lock file and one of them fails outright, a real risk here since this endpoint is only rate-limited, not serialized.
- **Pillow** (`backend/image_tools.py`) — convert/resize. Already a dependency (`extraction.py`'s OCR fallback). `resize-image`'s `target_size_kb` is only reliably honorable for JPEG (iterative quality reduction); for PNG/TIFF (lossless formats with no equivalent quality knob) it's a best-effort no-op beyond whatever dimension resize was also requested — documented, not silently wrong.
- **ocrmypdf** (`backend/ocr_tools.py: ocr_pdf()`) — wraps Tesseract specifically for embedding an invisible OCR text layer into a PDF (as opposed to `extraction.py`'s `pytesseract` calls, which return plain text for the classification pipeline). Chosen over hand-rolling text-layer embedding via PyMuPDF because that's exactly the one problem ocrmypdf is purpose-built to solve correctly (font metrics, exact glyph positioning so the invisible text lines up with the visible scan). `skip_text=True` (the default here, i.e. `force_ocr=False`) leaves any page that already has a text layer untouched and only OCRs the image-only pages, succeeding either way — this tool is "make my scan searchable," not "re-OCR everything," so a PDF that's already fully or partially text-layered is a normal success, never an error. (ocrmypdf's `PriorOcrFoundError` only fires when neither `skip_text` nor `force_ocr` is set, which this code never does — verified directly: calling `ocr_pdf()` twice in a row on the same already-searchable file does not raise.) Both Tesseract and Ghostscript are located by ocrmypdf via literal command name on `PATH` — pytesseract's own `tesseract_cmd` override (`extraction.py`) doesn't affect ocrmypdf's separate subprocess calls, so `config.py` prepends `TESSERACT_CMD`/`GHOSTSCRIPT_CMD`'s parent directories onto `os.environ["PATH"]` once at import time when those vars are set (Windows dev only — both are already on `PATH` in the Docker image via `apt-get`).
- **File validation**: every endpoint reuses `file_validation.matches_declared_type()` (magic-byte check) and a per-tool size cap (`tools_router.TOOLS_MAX_FILE_SIZE_BYTES` = 100MB, larger than the main pipeline's 20MB — `compress-pdf`'s whole purpose is handling large files, so a 20MB cap would rule out the main use case). `.docx`'s signature (`file_validation.py`) is the generic ZIP magic bytes (`PK\x03\x04`), since `.docx` is a ZIP archive under the hood — this only rules out non-ZIP content, not "a ZIP that happens not to be a real `.docx`," same caveat the app's other magic-byte checks already accept.

**Storage — a separate prefix, not a separate bucket**: output files live in the same Supabase Storage bucket as `documents`, under `tool-outputs/{user_id}/{uuid}_{filename}` (`backend/tools_common.py`) — visibly distinct from the main documents' flat `{uuid}{ext}` keys, without the overhead of provisioning/authenticating a second bucket for what's ultimately the same private-storage concern.

**Retention — a new `tool_files` table, not `documents`**: every output is tracked as a `ToolFile` row (see [Database](#database)) with an `expires_at` (`TOOLS_RETENTION_HOURS`, default 24h from creation). These are transient working files, not part of the document registry, so they get their own table rather than overloading `documents` with a `category`/`raw_text`-shaped row that would never be populated.

- **Cleanup mechanism**: `tools_common.cleanup_expired_tool_files()` runs as a dependency on every `/tools/*` request — a capped (50-row) sweep that deletes both the Storage object and the DB row for anything past its `expires_at`. This is the same "no real task scheduler on Render's free tier" constraint noted throughout this doc for `BackgroundTasks`/`slowapi`/the in-process caches — an opportunistic sweep piggybacking on real traffic is enough to keep the table/prefix roughly bounded without new infrastructure. `scripts/cleanup_tool_files.py` runs an uncapped sweep for when there's no traffic to trigger this lazily (e.g. an idle weekend) — run manually, or point an external scheduler at it later if this ever needs to be guaranteed rather than opportunistic.
- `GET /tools/{id}/download-url` also filters on `expires_at >= now()` directly (`tools_common.get_owned_tool_file()`), so a file past expiry 404s immediately even in the gap before the lazy sweep gets around to deleting it — same "owner + not-yet-expired" query shape as `main.py`'s `_get_owned_document()` uses for user isolation.

**Verified live**, against the real deployed Supabase project (not mocked), with real files, over real HTTP requests to a running server — not just unit-level function calls:

- **merge-pdf**: two real PDFs → downloaded the resulting file via its signed URL and confirmed (via `pikepdf`) it has exactly the combined page count.
- **compress-pdf**: a real, realistic 51.8MB scanned-style PDF (5 pages of uncompressed 200dpi page images, produced fresh for this test — a naive/unoptimized scan is exactly what this endpoint targets) → `low`/`medium`/`high` all produced valid PDFs with the original page count intact; `medium` (the default) came back at 0.48MB, a 99.1% reduction. (An earlier attempt using synthetic random-noise images gave misleading, non-monotonic results across presets — Ghostscript's automatic image-filter selection behaves very differently on incompressible noise than on real scanned-document content, so that test asset was rebuilt before drawing any conclusion.)
- **ocr-pdf**: a real PDF containing only a rendered image of text (genuinely zero embedded text layer, confirmed via PyMuPDF's `get_text()` returning empty before OCR) with a unique marker phrase → after `ocr_pdf()`, `get_text()` recovered the exact marker text, and PyMuPDF's `page.search_for(marker)` returned a real bounding box — proving an actual searchable/selectable text layer, not just "some text exists somewhere in the file."
- **split-pdf, pdf-to-docx, docx-to-pdf, convert-image, resize-image**: each run once over real HTTP with real files and its output downloaded and validated (page/paragraph/pixel-level checks, e.g. the DOCX round-trip's marker text and `resize-image`'s exact output dimensions).
- **Auth/validation/isolation**: no-token → 401; `merge-pdf` with fewer than 2 files → 400; a `.docx` upload that's actually plain text → 400 (magic-byte mismatch); one user requesting another user's `tool_files` row's download-url → 404.
- **Rate limiting**: 22 rapid calls to the same endpoint from one user → 18 succeeded, the rest 429'd.
- **Retention sweep**: force-expired a real row's `expires_at` directly in the DB, made one unrelated `/tools/*` call, and confirmed both the DB row and the underlying Storage object (re-download attempt → 404 from Supabase) were gone afterward. `scripts/cleanup_tool_files.py` was run separately and correctly reported deleting every remaining expired row.
- All test data (2 throwaway user accounts, ~28 tool_files rows/Storage objects created during this verification pass) was cleaned up afterward — the real project was left exactly as it was found.

**Testing**: `backend/tests/test_tools.py` — see [Testing](#testing) below.

**A dependency-pin fix along the way**: adding `pdf2docx`/`ocrmypdf` to `requirements.txt` surfaced two real version conflicts that a fresh `pip install -r requirements-dev.txt` caught immediately (this environment's own already-installed packages had silently drifted ahead of the pins from earlier standalone installs, masking it) — `pdf2docx` requires `PyMuPDF>=1.26.7` (the old pin was `1.24.10`) and `ocrmypdf` requires `Pillow>=12` (the old pin was `10.4.0`). Both were bumped (`pymupdf==1.28.2`, `Pillow==12.3.0`) and the full existing test suite (all of it, not just the new file) plus a direct manual check of `extraction.py`'s real OCR path were re-run afterward to confirm nothing in the main pipeline broke from the upgrade.

## E-signature

Phase 31. Self-serve signature capture + stamping: a user saves their own signature once (drawn or uploaded), then applies it to a PDF they already have in their registry. `backend/signature_router.py` (+ `signature_tools.py` for the actual stamping) implements it; `backend/models.py`'s `SignedDocument` and `users.signature_storage_path` back it — see [Database](#database) for both.

**Scope boundary — read this before extending this feature.** This is **self-serve signing only**: a user applies their own saved signature to their own document, in one request, with no other party involved. It is explicitly **not**:

- A multi-party signature-request workflow (e.g. "send this contract to someone else to sign and track whether they've signed it yet"). That needs real identity verification of the other party, an audit trail of who signed what and when (beyond this feature's plain `created_at`), possibly a public/anonymous signing link, and carries real legal-validity questions (e.g. eIDAS/ESIGN-Act-style considerations) that a POC-scale self-serve feature has no business quietly implying it satisfies.
- Anything claiming legal-grade e-signature compliance. This stamps an image onto a PDF — a visual mark, not a cryptographically verifiable signature (no PAdES/certificate-based signing, no tamper-evidence on the resulting PDF).

If a real request for either of those comes in, it's a substantially larger, separate phase — new data model (signer identity, invitation/status tracking, possibly a public route), not an extension of `POST /documents/{id}/sign`.

**Signature capture** (`POST /auth/signature`, Settings' Account tab — see [Settings](#settings)):

- Accepts a multipart `file` — either a PNG exported from the Settings page's own `<canvas>` (drawn with pointer events, `canvas.toBlob("image/png")`) or a directly uploaded PNG/JPEG. Validated the same way every other upload in this app is (`file_validation.matches_declared_type()` — magic bytes, not just the extension), capped at 2MB (`SIGNATURE_MAX_FILE_SIZE_BYTES`).
- Stored at a single fixed key per user, `signatures/{user_id}/signature{ext}` (in the same Supabase Storage bucket as everything else, a separate prefix — same pattern as `tool-outputs/{user_id}/`, see [Document tools](#document-tools)) — there is only ever **one** saved signature per user, not a history of them; saving again overwrites it (deleting the old Storage object first if the extension — hence the key — changed, e.g. replacing a drawn PNG with an uploaded JPEG).
- `users.signature_storage_path` references it; the API never exposes that raw path — `GET /auth/me` and `GET /auth/signature` both expose only `has_signature` (a `User.has_signature` Python property) plus, from the latter, a short-lived signed URL for previewing it (same 300s-expiry pattern as every other signed URL in this app).
- A transparent-background PNG falls out naturally from the canvas-drawing path with zero extra effort: nothing paints the canvas background, so only the drawn strokes end up non-transparent once exported — no explicit "make the background transparent" step was needed.

**Stamping** (`POST /documents/{id}/sign`, `backend/signature_tools.py: stamp_signature()`):

- 400s if the user has no saved signature yet ("Save a signature in Settings before signing a document"), and 400s if the target document isn't a PDF (checked via `Path(document.storage_path).suffix`) — only PDFs are signable in this phase.
- Uses **PyMuPDF** (`pymupdf`, already a dependency — see [Document tools](#document-tools)/`extraction.py`), not pikepdf's low-level object API and not a new dependency like `reportlab`: `Page.insert_image(rect, stream=...)` places an arbitrary image (transparency included, via the PDF's own soft-mask support) at a precise rectangle in one call — the simplest tool for exactly this job that was already in the dependency tree.
- **v1 placement is fixed, not user-configurable**: always the bottom-right corner of the **last** page, a constant `SIGNATURE_MARGIN_PT` (36pt) in from each edge, at a constant target width (`SIGNATURE_TARGET_WIDTH_PT` = 160pt, aspect-ratio-preserved from the signature image itself, clamped down for a narrow page). A target page number and x/y position were explicitly offered as a "v1 can skip this" simplification in this phase's own scope, and that's the option taken — a real, if narrow, refinement to add later, not a missing feature discovered after the fact.
- The **original** document is never modified — a signed PDF is a brand-new file, uploaded to its own Storage key under `signed-documents/{user_id}/` and tracked as a new `SignedDocument` row referencing the source `document_id`. Re-signing the same document creates another `SignedDocument` row rather than replacing the first — `GET /documents/{id}/signed` lists all of them (newest first), so a document that's been signed more than once keeps every version downloadable, not just the latest.
- **No retention sweep, unlike `tool_files`** (see [Document tools](#document-tools)): a signed document is a durable artifact the user deliberately created to keep (a completed, signed contract), not a transient working file — so `SignedDocument` has no `expires_at` at all. This is exactly why `delete_account()` (see [Settings](#settings)) had to be extended to explicitly clean up every `SignedDocument`'s Storage object (and the user's own signature image) before the user row cascades away — unlike `tool_files`, nothing would ever sweep these otherwise, and they'd be orphaned in Storage forever.

**Frontend**:

- **Settings → Account → Signature**: a Draw/Upload mode toggle. Draw mode is a `<canvas>` (pointer-event stroke drawing, a "Clear" button, `PointerEvent.setPointerCapture` so a stroke keeps tracking even if the pointer leaves the canvas mid-drag); Upload mode is a plain file input with a live preview (`URL.createObjectURL`). Either way, "Save signature" POSTs the resulting PNG/JPEG as multipart form data. The currently saved signature (if any) is shown above, fetched fresh from `GET /auth/signature` on mount, with its own "Remove signature" button.
- **Document detail page → "Signature" card** (`SignDocumentCard`, `documents/[id]/page.tsx`) — only rendered for a `.pdf` document. If the user has no saved signature, shows an inline note linking to Settings instead of a dead-end disabled button. Otherwise, "Sign document" opens a small confirm overlay (`SignPreviewModal`) showing *where* the signature will land — a static mock page outline with the real saved signature image overlaid in its actual bottom-right corner — before calling `POST /documents/{id}/sign` on confirm. This is a deliberately simple, hand-rolled overlay (not the `Dialog`/`@base-ui` wrapper already in `components/ui/` — checked, and it has zero usages anywhere in this codebase right now, so there was no established call pattern to follow) rather than a real PDF-page render, which would need a PDF-rendering library and is out of scope here. Any existing signed versions (`GET /documents/{id}/signed`) are listed below with their own download buttons, using the same popup-blocker-safe open-tab-then-navigate pattern as `ViewOriginalButton`/every other file download in this app.

**Verified live against the real deployment** (not just the mocked pytest suite below), through a fresh throwaway account: registered → uploaded a real, genuine 2-page PDF via `POST /documents/upload` → saved a real signature image via `POST /auth/signature` (confirmed `GET /auth/me`'s `has_signature` flipped to `true`) → called `POST /documents/{id}/sign` → downloaded the real signed PDF via its real Supabase-issued signed URL. Rendered the last page to a PNG and visually confirmed the signature appears correctly placed with a genuinely transparent background (no white box around it). Re-signing the same document was also verified live: a second `POST /documents/{id}/sign` call produced a second `SignedDocument` row, and `GET /documents/{id}/signed` correctly listed both. All test data (the throwaway account, its document, its signature, and both signed PDFs) was deleted afterward and confirmed gone via a direct query against the real database.

**Testing**: `backend/tests/test_signature.py` (15 tests) — see [Testing](#testing) below. Supabase Storage is mocked (an in-memory dict, patched at `signature_router`'s own imported names — this router imports its own copies of `upload_file_to_storage`/`download_file_from_storage`/`delete_file_from_storage`/`create_signed_url` from `storage.py`, so a shared fixture tuned for a different module's namespace, like `tools_common`'s, wouldn't patch anything here). The actual PDF stamping is never mocked: `test_sign_produces_a_real_stamped_pdf` runs the real `stamp_signature()` against a real 2-page PDF built with PyMuPDF and a real signature PNG built with Pillow, then re-opens the *produced* bytes with PyMuPDF and asserts on them directly (page count unchanged, exactly one embedded image on the last page) — the same "prove it with the real artifact, not just that the endpoint returned 200" discipline this app's other file-producing tests already follow.

## Document generation

Phase 32. Learns a document's field STRUCTURE from a sample Invoice or Agreement, then generates brand-new documents with the same shape but new content — filled in via a form or a plain-language instruction. `backend/templates_router.py` is the router; `template_learning.py` (Groq calls) and `template_generation.py` (rendering) do the actual work; `models.Template` + `documents.generated_from_template_id` back it — see [Database](#database).

**Scope boundary — read this before extending this feature.** This produces a new, cleanly formatted document containing the same fields/sections/structure as the sample (same line-item table columns, same header fields, same section order) — it does **not** guarantee pixel-identical visual output to the sample (exact original fonts, logo position, exact spacing). True visual-layout cloning is a distinct, harder problem — real PDF coordinate/layout extraction and positioned re-rendering — and is explicitly **not attempted here**; flagged as a possible future phase if it's ever actually needed, not something this phase quietly falls short of.

**Step 1 — learning a schema, never values** (`POST /templates/learn-from-sample`, `template_learning.learn_field_schema()`):

- Uploads the sample exactly like `POST /documents/upload` does (same validation, same Storage upload, same real `documents` row — so the sample itself is an ordinary, visible document, not a hidden side-channel upload), then — **synchronously**, not backgrounded, since the caller needs the learned schema back in this same response — runs `extraction.extract_text()` and `classification.classify_text()` (the same two functions the main pipeline uses), skipping structured extraction entirely (which would extract *this one sample's* values, the opposite of what's needed).
- 400s if the classified category isn't `Invoice` or `Agreement` (`SUPPORTED_TEMPLATE_CATEGORIES`) — matching this phase's two stated primary use cases. The sample document itself is still saved either way (a real, legitimate upload); only template creation is refused. Adding a third category later means adding it to this one set plus (if the category needs new prompt guidance) `template_learning.py` — no rebuild, no schema-format change.
- The learned `field_schema` (JSONB, stored on `Template.field_schema`) is an ordered list of **sections**, each either a flat set of **fields** or a line-item-style **table** of **columns** — every field/column has a `key` (snake_case), a `label` (human-readable), and a `type` (`string`/`number`/`date`). A `table` section only appears if the sample genuinely had one (e.g. an invoice's items table) — an Agreement's learned schema typically has none. The Groq prompt explicitly instructs the model to describe the document's *shape only* — no real names, numbers, dates, or amounts from the sample are ever asked for or allowed through; `template_learning.normalize_schema()` then defensively drops any malformed section/field the model returns rather than trusting its output shape blindly (same "validate, don't just trust the model" pattern as [Analytics](#analytics)'s `known_values` check).
- A real gotcha hit and fixed here: the schema's own JSON-shape description (used inside the system prompt to show Groq the exact shape to return) contains literal `{`/`}` characters — building the final prompt with `str.format()` on a string that already had this description concatenated in caused Python to mis-parse those literal braces as format placeholders (`KeyError: '\n  "document_type"'`). Fixed by building that one prompt via an f-string (only `{category}` is ever substituted) instead of `.format()` on the combined string — caught by `test_learn_from_sample_happy_path`, which exercises the real prompt-building code path, not just a mocked Groq response shape.

**Step 2 — generating a new document** (`POST /templates/{id}/generate`):

- Accepts **either** `{"values": {...}}` (matching the template's schema — a "fields" section's value is `{field_key: value}`, a "table" section's value is an array of `{column_key: value}` rows) **or** `{"instruction": "..."}` (free text, e.g. *"generate an invoice for Vendor X, amount 50000, due in 30 days"*), parsed into the same shape by `template_learning.parse_instruction_to_values()` — a Groq call given the template's own schema and today's date (so "due in 30 days" resolves to a real ISO date). 400s if neither is given.
- **Both paths are forced through `template_learning.normalize_values()`** before rendering — it rebuilds the values object using *only* the schema's own known section/field keys, regardless of what the request body or the model actually returned. A stray or invented key (from a sloppy client request, or a model hallucinating an extra field) is silently dropped, never rendered and never stored — verified directly by `test_generate_ignores_extra_unknown_keys_in_values`.
- **Rendering uses ReportLab, not WeasyPrint** (`template_generation.render_document()`) — a deliberate choice given this phase's own offered options. WeasyPrint needs a GTK/Pango/Cairo system runtime (real, previously-hit friction on this Windows dev machine installing Ghostscript/LibreOffice/Tesseract — see [System dependencies](#system-dependencies)); ReportLab is pure Python, already resolvable with zero new system dependencies (`pip install reportlab`, using the already-installed Pillow underneath). Since this phase's scope is explicitly "clean professional formatting," not CSS-level styling fidelity, ReportLab's Platypus layout engine (a title, then one flowable block per section — a bordered `Table` for a table section, a borderless label/value `Table` for a fields section) is already the right tool with no HTML/CSS layer needed in between.
- **The result is an ordinary `documents` row — there is no separate "generated documents" table.** Its `category` is already known (the template's own — no reclassification needed), and the filled-in `values` already *is* its structured data (there was never a values-extraction step to skip), so it's created directly with `status="processed"`, `extracted_json`, `raw_text`, and (best-effort) `deadline_date` all populated in this one request — no background pipeline, no polling. This means a generated document is immediately downloadable via the existing `GET /documents/{id}/download-url`, chattable via the existing `POST /documents/{id}/chat`, and full-text searchable via the Copilot's `search_document_text` — all for free, with zero new code path needed for any of them.
- **`extracted_json`'s shape is deliberately self-describing, not the fixed flat-key shape `structured_extraction.py`'s `SCHEMAS` use for a normally-uploaded Invoice/Agreement**: `{"_generated": true, "_field_schema": <the template's schema>, "_values": <the filled-in values>}`. A *learned* template's field keys are whatever Groq named them from that specific sample — not guaranteed to match the fixed schema's own names (e.g. the real sample used for live verification below produced `due_date`/`bill_to`/`total_due`, not necessarily what a hand-written schema would have chosen) — so pretending it fits the fixed `FIELD_SECTIONS`/`FIELD_LABELS` convention (see [Categories](#categories)) would silently render blank fields on the document detail page despite real data existing. Instead, `documents/[id]/page.tsx`'s `ExtractedCards` checks `extracted._generated` first and, if set, renders generically via `GeneratedDocumentCards` — walking `_field_schema.sections` and pulling values from `_values` directly, with its own generic table renderer for a `table`-type section — bypassing `FIELD_SECTIONS` entirely for these documents.
- **`documents.generated_from_template_id`** is the reverse link (which template produced this document) alongside `templates.created_from_document_id` (which sample document a template was learned from) — genuinely a mutual FK relationship between the two tables (`documents` and `templates` each reference the other). This is a real circular dependency that broke `Base.metadata.create_all()`/`drop_all()` (used by the test suite — see [Testing](#testing)) with `CircularDependencyError` until fixed: `Document.generated_from_template_id`'s `ForeignKey` sets `use_alter=True` plus an explicit constraint name (`fk_documents_generated_from_template_id`), telling SQLAlchemy's metadata sorter this one FK can be added/dropped as a separate step, breaking the cycle — this changes nothing about how the constraint behaves at query time, only how generic schema-management tooling orders DDL around it.
- **Both `Template.created_from_document_id` and `documents.generated_from_template_id` are nullable with `ON DELETE SET NULL`**, not `CASCADE`: deleting the original sample later shouldn't delete an already-learned, independently useful template; deleting a template later shouldn't delete a document someone already generated and is using.
- **Rate limiting**: both `POST /templates/learn-from-sample` and `POST /templates/{id}/generate` share the same `20/hour` per-user shape as every other AI-calling/compute-heavy endpoint in this app — see [Rate limiting](#rate-limiting).

**Bug fix — a generated document's user-facing filename was showing a raw UUID.** Real symptom: a generated document downloaded/displayed as something like `440593cc-93f5-4349-8420-b9276ee08387_Invoice_a34cdcec.pdf`. Root cause, confirmed by reading the actual code rather than guessed: `generate_document()`'s old scheme built `output_filename = f"{category}_{uuid4().hex[:8]}.pdf"` (already a bit opaque, but not the visible bug) and then `storage_path = f"generated-documents/{user_id}/{uuid4()}_{output_filename}"` — a **second**, full UUID prefixed onto that. Nothing in `main.py` ever stores this `storage_path` string as a filename anywhere — the real leak was on the frontend/download side: `GET /documents/{id}/download-url` returns a bare Supabase signed URL with no `Content-Disposition` filename override, so the one existing way to get the file onto disk (`ViewOriginalButton`: open the signed URL in a new tab, then the browser's own "Save As") falls back to naming the file after the URL's own last path segment — which *is* `storage_path`'s basename, UUID prefix and all. **Regular uploads were never affected the same way**, confirmed by reading `POST /documents/upload` (`main.py`): it already stores the original uploaded filename (`file.filename`) as `documents.filename`, completely decoupled from its own separate UUID-only `storage_path` key (`f"{uuid4()}{extension}"`) — this bug was specific to the generated-document path in `templates_router.py`.
  - **Fix, two parts.** (1) `template_generation.build_generated_filename(category, field_schema, values)` (new function) derives a real, human-readable name — e.g. `"Invoice - Lighthouse Media Solutions Pvt. Ltd. - 2026-03-15.pdf"` — by reusing the renderer's own field-classification machinery (`_build_layout_plan`/`_classify_field`/`_issuer_role`) to find the issuer's own name (the "vendor" on a generated Invoice — preferred first, matching this app's existing `vendor_name` convention for uploaded invoices) or, failing that, the first name-like field in any party group (e.g. `bill_to_name`), plus a ref-section date field if one exists (e.g. `invoice_date`, never a due/expiry/delivery deadline field, which classifies elsewhere). Falls back to `"Generated {category} - {timestamp}.pdf"` only when no party name is derivable at all (a schema/template with no vendor/party-shaped field, or none filled in this time) — never a bare UUID. A value is sanitized (`_sanitize_filename_part`) against filesystem-unsafe characters (`<>:"/\|?*` and control characters) before being used; the assembled *whole* name (not each part individually) is trimmed of a trailing dot/dash/space, so a legitimate abbreviation like "Pvt. Ltd." isn't mangled into "Pvt. Ltd" just because it happens to be the last part when no date is available. (2) `templates_router.generate_document()` now calls this for `output_filename`, and `storage_path` was simplified to `f"generated-documents/{user_id}/{uuid4()}.pdf"` — a UUID only, never concatenated with any user-facing name. This is also the general rule going forward: a UUID belongs only in a Storage key, never in anything a user sees as a filename.
  - **Verified**: `backend/tests/test_template_generation.py` gained 3 direct tests (`build_generated_filename` produces the exact expected human-readable name and contains no UUID; the no-derivable-name fallback also contains no UUID; unsafe characters in a party name are stripped) and `backend/tests/test_templates.py` gained an HTTP-level regression test confirming a real `POST /templates/{id}/generate` response's `filename` is human-readable and UUID-free while `storage_path` (which does still legitimately contain a UUID, server-side only) is never equal to it.

**PDF design — rebuilt from a flat label/value list into a real business-document layout.** The original Phase 32 renderer (one borderless label/value `Table` per section, no letterhead, no visual hierarchy) was judged not good enough for a real generated invoice/agreement and completely rewritten in `template_generation.py`, still ReportLab/Platypus (same reasoning as above — no new system dependency), still schema-agnostic (a learned template's field keys are arbitrary, so nothing here is hardcoded to a fixed field list):

- **Field classification, not fixed field names.** Because a template's `field_schema` comes from whatever a language model named the sample's fields, every visual block (letterhead header, party grid, totals box, notes box, bank details, signature) is populated by a token-based classifier (`_classify_field()` / `_tokens()`) that splits each field's snake_case `key` on non-alphanumeric characters into a set and checks *set membership* against role keyword lists — deliberately not substring/regex matching, to avoid a false positive like `"expansion"` matching `"pan"`. Priority order per field: issuer → party-identifier → party → ref → totals → notes → bank → leftover. A block that finds no matching fields simply doesn't render — no empty boxes for a sparse or non-Invoice schema (e.g. a plain Agreement with only a `party_names` field renders just that, plus the always-present title/signature, and nothing else).
- **Layout, top to bottom**: centered bold title → two-column letterhead header (issuer name/address left, GSTIN/PAN/CIN right, `VALIGN: TOP` so both columns start at the same y) → horizontal rule → bold-label reference row (invoice number/date etc.) → a bordered, shaded-header party grid (one box per distinct party role — e.g. "Bill To" and "Ship To" render as separate side-by-side boxes via a nested `Table`, not merged) → the line-items table (shaded header row, vertical column dividers, `repeatRows=1`) → a visually distinct bordered totals box (a bold/larger font row for whichever field looks like the grand total) → an Indian-numbering amount-in-words line derived from that same grand total → a highlighted/tinted/bordered notes box → a plain bordered bank-details box → a signature block (space for an embedded signature image, then the issuer name, then "Authorised Signatory").
- **Cells that need to wrap use `Paragraph`, not plain strings.** A ReportLab `Table` cell holding a bare string never wraps or grows the row — this is what made the original renderer's line-items table silently truncate/overlap long descriptions. Every line-items cell is now built as a `Paragraph` flowable, so a long description wraps and the row height expands to fit — verified with a deliberately long description (see Testing below) that survives in full, word-for-word, in the rendered output.
- **Real page-count-aware pagination — `_BorderedNumberedCanvas`.** The outer page border and the "Page X of Y" footer both need the *final* page count before they can be drawn correctly on page 1, which Platypus doesn't know until the whole document has been laid out. Solved with the standard ReportLab "NumberedCanvas" pattern: a `canvas.Canvas` subclass whose `showPage()` buffers each page's canvas state instead of finalizing it, and whose overridden `save()` only then loops back over every buffered page — now that the true total is known — drawing the border/footer on each before actually calling the real `showPage()`. Verified directly: a genuine 2-page document (forced via a 60-row line-items table) shows a correct border and "Page 1 of 2"/"Page 2 of 2" footer on both pages, and the line-items table's header row genuinely repeats on the second page (not just configured to — checked that the header text literally appears on both pages' extracted text).
- **The signature block is never pinned to a fixed bottom coordinate.** It's wrapped in `KeepTogether(...)` so its own lines never split across a page boundary, but otherwise flows naturally with the rest of the story — it lands on the current page if room remains, or starts a fresh page if not, and is never stranded alone on an otherwise-blank page. Verified with both a short single-page document (signature lands on the same page, no forced second page) and a long multi-page one (signature starts cleanly near the top of its own page, not orphaned).
- **Signature image, reusing Phase 31's saved signature.** `render_document()` takes a new keyword-only `signature_image_bytes: Optional[bytes] = None` parameter (default `None` so all pre-existing callers/tests are unaffected). `templates_router.generate_document()` fetches the current user's saved signature via `download_file_from_storage(current_user.signature_storage_path)` (see [E-signature](#e-signature)) when one exists, and passes the bytes through; `_render_signature_block()` embeds it via `ImageReader`/`Image` (aspect-ratio preserved), falling back to blank space above "Authorised Signatory" for a user with no saved signature. The fetch is best-effort — a transient Storage failure logs a warning and generation proceeds with a blank signature area rather than failing the whole request.
- **Amount-in-words uses real Indian lakh/crore numbering, computed in Python — never trusted from the model.** `india_validation.number_to_indian_words()` (new function, same module as the existing GSTIN-checksum/`parse_indian_number()` logic) converts a grand-total float into words using crore=10,000,000/lakh=100,000 grouping (not western thousand/million), consistent with this app's established "don't trust an LLM with arithmetic that can be computed exactly" philosophy. Verified against known values before being trusted for real document generation, including the exact figure this feature's own live verification used: `165000 * 1.18 = 194700.0` → `"One Lakh Ninety Four Thousand Seven Hundred"` (also checked: 25000000 → "Two Crore Fifty Lakh", 999999999 → "Ninety Nine Crore Ninety Nine Lakh Ninety Nine Thousand Nine Hundred Ninety Nine", paise handling, negative amounts, zero).
- **Two real bugs found and fixed during this rebuild's own live verification** (both caught by actually looking at the rendered PDF, not just asserting on extracted text):
  1. **Notes classification missed the plural field-key form.** The notes-detection keyword list only checked for the singular token `"note"`, but a real field key like `notes_gst` tokenizes to `{"notes", "gst"}` — a set-membership miss, not a substring miss. A document with fields named `notes_gst`/`notes_tds` rendered them via the generic leftover-section layout instead of the intended highlighted notes box. Fixed by adding `"notes"`/`"term"`/`"terms"`/`"remarks"` to the word list (and, proactively, plural forms like `"totals"`/`"taxes"`/`"subtotals"` to the totals classifier for the same class of robustness). Verified by regenerating and confirming both notes now render together inside the correct tinted/bordered box.
  2. **The title rendered left-aligned instead of centered**, contradicting the explicit "centered, bold, prominent" requirement — a plain authoring mistake (`alignment=TA_LEFT` was set explicitly on the title style, overriding ReportLab's own default-centered `Title` base style). Only caught by viewing the rendered page, since centering has no text-extractable signal. Fixed to `TA_CENTER`.
- **Verified live** by generating the task's own exact proforma-invoice scenario — Lighthouse Media Solutions Pvt. Ltd. (issuer) → Coastal Retail Group Pvt. Ltd. (bill-to), ₹1,65,000 advertisement-charges line item, CGST+SGST @ 9% each = ₹1,94,700 total — and visually confirming, page by page, every element from the design spec: centered bold title; letterhead with GSTIN right-aligned at the same y as the company name/address; horizontal rule; bold-label reference row; a bordered/shaded "Bill To" box; a bordered line-items table with the long description wrapping correctly (no truncation, no overlap); a visually distinct bordered totals box with a bold/larger grand-total row; the correct amount-in-words line ("Rupees One Lakh Ninety Four Thousand Seven Hundred Only"); both GST and TDS notes together inside the highlighted tinted/bordered notes box (post-fix); a bordered bank-details box; and, on a natural second page, the signature block positioned near the top (not stranded, not overlapping) with the outer border and correct "Page X of Y" footer present on both pages. Also verified graceful degradation on a sparse schema (no crash, no empty placeholder boxes for absent categories) and real signature-image embedding (confirmed via PyMuPDF's `get_images()` and visual inspection that a transparent-background PNG renders correctly above "Authorised Signatory").

**Second live-verification pass — confirming the design genuinely generalizes across structurally different templates, not just one invoice shape.** The first pass above only ever exercised one real Invoice-shaped schema; a later request specifically asked to verify with a second, genuinely different real template (an Agreement, not just a second Invoice) and to confirm the classifier's word lists — not the document's fixed shape — are what drives the layout. This surfaced three real, previously-undetected gaps, all found by actually generating from **real Groq-learned schemas** (`template_learning.learn_field_schema()` called for real against a genuine sample Tax Invoice and a genuine sample Residential Lease Agreement, not hand-authored test schemas that would only exercise field names already known to match), rendering, and looking at the pages:

1. **`_PARTY_QUALIFIERS` only covered invoice/PO terminology.** The real learned lease schema's `landlord_name`/`landlord_address`/`tenant_name`/`tenant_address` fields (none containing `bill`/`ship`/`buyer`/`vendor`/`client`/`customer`/`party`) all fell through to the generic leftover renderer — **exactly the "flat, unstyled label:value list" failure mode this whole redesign exists to prevent**, reproduced live rather than assumed. Fixed by extending `_PARTY_QUALIFIERS`/`_PARTY_GROUP_LABELS` with common two-party legal-document role vocabulary: `landlord`/`tenant`, `lessor`/`lessee`, `licensor`/`licensee`, `employer`/`employee`, `contractor`, `consultant`, `borrower`/`lender`, `guarantor`, `disclosing`/`receiving` (NDA), `recipient`, `consignor`/`consignee`, `purchaser`, `owner` — the same token-set-membership mechanism as the original list, just a bigger vocabulary, never a fixed "this is a lease" branch anywhere. Also fixed: generic `party_a`/`party_b`/`first_party`/`second_party` naming (which a model reaches for when it can't identify domain-specific role names, e.g. for an NDA) previously collapsed both sides into one shared "Party Details" box, since neither key has anything more specific than the bare `party` token — `_party_group_label()` now checks for `a`/`b`/`first`/`second` sub-tokens to keep them as two genuinely separate boxes.
2. **The totals bucket's keyword list was GST-invoice-specific** (`subtotal`/`total`/`tax`/`cgst`/`sgst`/`igst`), so the lease's `monthly_rent`/`security_deposit` — real headline monetary figures — never got the bordered-box treatment at all. ## Document source separation

A real bug found post-launch: template-learning samples (`POST /templates/learn-from-sample`) and template-generated documents (`POST /templates/{id}/generate`) were showing up in the main "My Documents" list (Home and the `/documents` Registry page) and its stat-tile counts, even though both belong conceptually to the Editing Workspace's Templates feature, not the document registry a user actually uploads to.

**Root cause**: both are, by design, ordinary `documents` rows (see [Document generation](#document-generation) — this was a deliberate choice, so a generated document gets full document features — chat, download, full-text search — for free). Nothing distinguished either kind of row from a normal upload: `generated_from_template_id` existed but only ever marked a generated document, and a template-learning sample had no marker at all (only an indirect, reverse pointer — `templates.created_from_document_id` — pointed back at it). `GET /documents`/`GET /documents/deadlines` had no filter on either signal, so every sample and every generated document leaked straight into the main list.

**Fix — `documents.source`** (migration `0018_add_source_to_documents`, `models.Document.source`): a `NOT NULL` text column, one of `upload` / `template_sample` / `generated`, indexed since `GET /documents` filters on it every call. Backfilled for existing rows from the two signals that already existed: `generated_from_template_id IS NOT NULL` → `generated`; `id` appearing as some `templates.created_from_document_id` → `template_sample`; everything else defaults to (and stays) `upload`. Set explicitly at creation time in the two write paths (`templates_router.py`'s `learn_from_sample`/`generate_document`) rather than relying only on the column's default, since the main `POST /documents/upload` path is the one that should get the default (`source="upload"`) for free.

- **`GET /documents`** (see [API endpoints](#api-endpoints)) now always filters `Document.source == "upload"`, in addition to its existing `user_id`/`category`/date filters — hardcoded, not a query parameter, since the main list should never show these rows under any filter combination. Since this filter is fixed rather than parameterized, `documents_cache`'s cache key (`main.py`) didn't need a new dimension.
- **Two new endpoints power the Workspace instead**: `GET /documents/templates` (`source == "template_sample"`) and `GET /documents/generated` (`source == "generated"`), both scoped to the current user, both plain `DocumentListOut` lists, newest first, uncached (small, infrequently-viewed lists — not worth a `TTLCache` entry). See [API endpoints](#api-endpoints).
- **Every single-document endpoint is deliberately left unfiltered by `source`** — `GET /documents/{id}`, `GET /documents/{id}/download-url`, `POST /documents/{id}/chat`, etc. A template sample or generated document is still a completely ordinary, fully-featured document once you already have its id; only the *list* endpoints needed to change.

**Frontend**: `TemplatesPanel.tsx` (see the `/workspace` entry in [Frontend pages](#frontend-pages)) renders two new sections, "Uploaded Templates" and "Generated Documents", each row showing the filename and upload date plus two icon-only buttons (`lucide-react`'s `Eye`/`Download`, matching this app's existing icon-button style — see `DownloadRowButton` in `DocumentsTable.tsx`), each with a `title` (tooltip) and `aria-label`. **Open** reuses the existing document detail page (`/documents/[id]`) rather than a new viewer — it links to `/documents/{id}?from=workspace`, and the detail page (`documents/[id]/page.tsx`) reads that query param via `useSearchParams()` to send its back-link and post-delete redirect to `/workspace` instead of `/documents` when present (`returnTo`/`returnLabel`, computed once near the top of the component). **Download** reuses the exact same `downloadSignedFile()` helper (`lib/download.ts`) and `GET /documents/{id}/download-url` endpoint every other download button in this app already uses — same per-user ownership check (`_get_owned_document`, 404 for anything not owned), same private-Storage signed-URL mechanism, no new backend download path. Both lists refetch (`refreshKey` state bumped on the panel) right after a new sample is learned or a new document is generated, so a freshly-created row appears without a manual page reload.

**Deliberately left unchanged — flagged, not fixed, per this feature's own scope**: `GET /documents/deadlines`, Analytics, and Copilot were **not** given a `source` filter. Checked directly, not assumed:

- **Deadlines/Tasks**: a template-generated document can have a real `deadline_date` (`template_generation.guess_deadline_date()`), and `GET /documents/deadlines` has no `source` filter — so a generated document with a deadline **does** currently appear on the `/tasks` page and in its stat tiles. A template-learning sample never has a `deadline_date` (structured extraction is skipped for it — see [Document generation](#document-generation)), so samples never appear here regardless.
- **Analytics**: `compute_schema_summary()` (`analytics.py`) iterates every key in `extracted_json` with no `source` filter and no leading-underscore skip. A generated document's `extracted_json` shape is `{"_generated": true, "_field_schema": {...}, "_values": {...}}` (see [Document generation](#document-generation)) — so today, a generated document actively **pollutes** a category's Analytics field list with three fake fields (`_generated` as a boolean, `_field_schema`/`_values` as opaque "object"-typed fields), not just "shows up," a real latent bug independent of this one. A template-learning sample's `extracted_json` is `null` (structured extraction is skipped), so it contributes nothing to Analytics either way.
- **Copilot**: none of its four tools (`list_documents`, `get_document_count`, `get_deadline_summary`, `search_document_text`) filter by `source` — a generated document's `raw_text` (a plain-text rendering of its own values) is fully searchable/citable, and both a sample and a generated document count toward `get_document_count`'s totals.

Whether to extend the `source` filter to any of these three is an open decision for whoever owns this feature next — not made here.

## Editor assistant

Phase 23. A natural-language layer over the `/tools/*` endpoints above: `POST /editor/chat` (`backend/editor_router.py` + `backend/editor_chat.py`) lets a user describe what they want ("merge these and compress the result under 10MB") instead of manually picking a tool and its options in the `/editor` page's UI (see the `/editor` entry in [Frontend pages](#frontend-pages)). Both paths — the manual tool picker and this chat panel — call the exact same underlying transform functions and land in the exact same `tool_files` table via the exact same `tools_common.save_tool_output`, so a file the assistant produces is completely ordinary: downloadable via `GET /tools/{id}/download-url`, subject to the same 24h retention sweep, no separate code path to keep in sync.

- **Tool definitions**: all 8 `/tools/*` operations (`editor_chat.TOOL_DEFINITIONS`) are defined as Groq function-calling schemas (name, description, JSON-schema parameters) — `merge_pdf`, `split_pdf`, `compress_pdf`, `pdf_to_docx`, `docx_to_pdf`, `convert_image`, `resize_image`, `ocr_pdf`. `compress_pdf`'s schema takes an optional `target_size_kb` in addition to `quality` — the endpoint itself only accepts `quality`, so `editor_chat._compress_to_target()` translates a size goal into repeated `compress_pdf()` calls, walking `high → medium → low` and stopping as soon as the result is under target (or reporting the best it could do at `low`, honestly, if not — verified live, see below).
- **Model**: `openai/gpt-oss-120b`, same as `classification.py`/`chat.py`, with `tools=TOOL_DEFINITIONS`, `tool_choice="auto"`, `reasoning_effort="low"`. Confirmed live (a throwaway smoke test, not assumed from docs) that this model actually supports Groq tool-calling before building anything around it.
- **Agentic tool-calling loop** (`editor_chat.run_editor_chat()`): call Groq → if it responds with plain text, that's the final answer (a clarifying question, a decline, or a wrap-up summary) and the loop ends; if it responds with one or more `tool_calls`, each is executed immediately, its result (or error) is fed back as a `"tool"` role message, and Groq is called again — repeating until a plain-text response arrives or `MAX_TOOL_ROUNDS` (5) is hit. This is the standard mechanism for chaining ("merge these, then compress the result"): the model can't know the merged file's name until the merge actually runs, so round 2's `compress_pdf` call references the filename reported back from round 1's tool result, not something the model invented upfront.
- **File resolution** (`editor_chat.ChatFileContext`): a tool argument like `"file": "merged.pdf"` is resolved by filename, checked in order against (1) files produced earlier in this *same* turn's loop (enables the chaining above), (2) files uploaded with this HTTP request, (3) `context_tool_files` — {id, filename} pairs the frontend passes for files produced in an *earlier* chat turn (or even a manual tool run), fetched from Storage on demand via the same `download_file_from_storage` the rest of the app uses. An unresolvable filename (typo, hallucination, expired reference) raises a `ChatToolError` whose message is fed straight back to Groq as the tool result — the model sees the failure and can react (apologize, ask the user to re-check the name) instead of the whole request 500ing.
- **Design decision — every chat turn resends the full current file set, no separate upload-then-chat step**: same reasoning as the manual `/tools/*` endpoints (see above) — simplicity over a staging flow, at the cost of re-uploading bytes the backend may already have from a prior turn (mitigated for *produced* files by `context_tool_files`, which needs no re-upload at all).
- **Staying on-topic**: the system prompt (`editor_chat.SYSTEM_PROMPT_TEMPLATE`) explicitly scopes the assistant to file editing/conversion only — no general-knowledge questions, no document classification/extraction advice (a different, separate part of the app). An early smoke test without this constraint answered "what is the capital of France?" directly; after tightening the prompt, verified live that the same kind of off-topic question gets a plain decline-and-redirect instead.
- **Clarifying questions, not guesses**: the prompt instructs the model to ask a short question rather than invent a value whenever a tool needs information the user didn't give (resize dimensions/target size, image convert's target format, which files to merge and in what order). Verified live: "resize my photo" with no size info gets asked "What width, height, or target size...?" with zero tool calls made.
- **Rate limiting**: same `20/hour` per-user limit as the direct `/tools/*` endpoints (`rate_limit.user_or_ip_key`) — if anything more conservative given one chat turn can trigger several chained tool calls plus multiple Groq round trips. See [Rate limiting](#rate-limiting).
- **Verified live** against the real deployed Supabase project and the real Groq API (not mocked) — a simple single-tool request (merge two real PDFs), the exact chaining example from this phase's own spec ("merge a.pdf and b.pdf and then compress the result to under 2KB" — correctly ran merge then compress in sequence, and honestly reported the 2KB target wasn't fully reachable rather than pretending success), cross-turn chaining (a second, separate request with no files attached, referencing an earlier turn's `merged.pdf` purely via `context_tool_files`, correctly split it into 2 pages), and all three non-tool paths (ambiguous request, off-topic question, unsupported request) — each produced the expected response with zero tool calls. All results were downloaded and validated as real, valid files (`pikepdf` page-count checks). All throwaway accounts/`tool_files` created during this verification were cleaned up afterward.

## Copilot

Phase 25. A second, distinct AI layer from the Editor assistant above: `POST /copilot/chat` (`backend/copilot_router.py` + `backend/copilot_chat.py`) answers questions about the user's whole document **registry** (deadlines, categories, document contents), not about editing/converting files. Surfaced as a persistent, global sidebar (`CopilotPanel`, see [Frontend pages](#frontend-pages)) available on every authenticated page, not scoped to one document — distinct from `/documents/[id]`'s own `ChatCard`, which only ever answers questions about that one document's `raw_text`. Same agentic tool-calling loop shape as `editor_chat.py` (see [Editor assistant](#editor-assistant)) — kept as its own copy rather than a shared helper, for the same "only two call sites" reasoning given there.

**Two genuinely different kinds of question, on purpose**:

- **Structured questions** ("show all active agreements", "which invoices are overdue") are answered from existing database fields (`category`, `status`, `deadline_date`) — no new infrastructure, just real queries.
- **Content questions** ("find contracts mentioning exclusivity") need to search inside `raw_text`, which this phase adds via Postgres **full-text keyword search** (`documents.search_vector`, a generated `tsvector` column + GIN index — see [Database](#database)), not true semantic/embedding-based search. This was a deliberate scope call, not an oversight: real semantic search needs embeddings, a vector column, and a similarity index — meaningfully more infrastructure, and was already earmarked as its own later phase back when `documents_table`'s migration first enabled the (still-unused) `pgvector` extension "for embeddings added later" (see [Database](#database)). Full-text search gets a working copilot now, honestly. Both the tool's own description and the system prompt say outright that this is keyword search, not meaning-based search, so the assistant doesn't imply it's smarter than it is — verified live (see below) that a semantically-related-but-differently-worded query ("sole rights to sell a product" against a document that says "exclusivity", never "sole rights") correctly comes back with zero results and an honest "none of your documents contain that exact wording" instead of a false negative dressed up as confidence.

**Tools** (`copilot_chat.TOOL_DEFINITIONS`, all scoped to `current_user.id` — see [Per-user document isolation](#per-user-document-isolation)):

| Tool | Backs | Notes |
|---|---|---|
| `list_documents(category?, status?, deadline_before?, deadline_after?)` | structured questions | Up to 20 results, newest first. Called with no arguments at all, returns the whole registry. The tool description explicitly steers the model to use this (with `category` + a deadline bound) for a *single-category* deadline question like "which invoices are overdue", rather than `get_deadline_summary` — see the tool-selection fix below. |
| `get_document_count(category?, status?)` | count/total questions ("how many documents/invoices/files do I have") | A real, uncapped `SELECT count(*)` — added after a live bug report (see below) found the model had nothing to reach for on a pure counting question, and `list_documents` would have been the wrong fix anyway: it caps at 20 rows, so counting its results would silently under-report past that. No citations (nothing specific to link to for a bare number). |
| `get_deadline_summary()` | cross-category deadline questions ("what's overdue overall") | Overdue/due-soon counts + short lists (up to 10 each), using the real `current_user.due_soon_threshold_days` — not a hardcoded 30 days, unlike `GET /documents/deadlines?urgency=due-soon`'s own server-side default (see [Settings](#settings)) — since this tool has `current_user` in scope to do it properly from the start. |
| `search_document_text(query)` | content questions | Real Postgres full-text search: `plainto_tsquery('english', query)` against `search_vector` (English stemming — "exclusive" also matches "exclusivity"), ranked by `ts_rank`, with a `ts_headline`-generated snippet per match, capped at 10 results. |

- **Today's date is injected into the system prompt** (`SYSTEM_PROMPT_TEMPLATE.format(today=...)`) — an easy-to-miss LLM gotcha: without it, the model has no way to compute `deadline_before=<today>` for an "overdue" question at all. Discovered via a live test, not anticipated in advance: an early version's answer to "which invoices are overdue" was technically correct but visibly confused (it called the cross-category `get_deadline_summary`, got back an overdue GST document mixed in with the overdue invoice, and its prose started with "two invoices are overdue" before self-correcting mid-sentence). Fixed by (a) telling the model today's date and (b) sharpening both tools' descriptions on when to prefer the category-scoped `list_documents` over the cross-category summary — re-verified with the exact same query 3 times in a row afterward, getting the same clean, single-citation answer every time.
- **Citations**: every document any tool call actually returned this turn is deduplicated (by id) into a flat `citations` list on the response (capped at 20), independent of the model's own prose — the frontend renders these as their own clickable cards rather than depending on the model to format links correctly in free text, the same design choice `editor_chat.py`'s `tool_runs` already made for file downloads. Trade-off, stated plainly: this is "every document surfaced by a tool call," not "every document the final sentence specifically mentions" — a well-scoped tool call (e.g. `list_documents(category="Invoice", ...)`) already keeps this tight in practice.
- **No markdown in replies**: the system prompt explicitly forbids `**bold**`/bullet lists/headers — caught live (see below) when an early answer rendered literal, un-rendered asterisks in the plain-text chat bubble; the prompt now tells the model the UI already shows matching documents as separate cards, so it doesn't need to format or repeat a list itself.
- **Bug found post-launch — "how many total files do I have" got "no tool for that"**: none of the original 3 tools' descriptions, nor the system prompt, ever said what a bare count/total question should map to, and `list_documents` (the closest fit) both undersells itself (its description never mentioned that calling it with zero arguments returns everything) and would have been the wrong tool regardless — its 20-result cap means counting its output would silently under-report a bigger registry. Fixed by adding the dedicated `get_document_count` tool above (a real uncapped `count(*)`, not list-then-count), sharpening `list_documents`' own description to point count-style questions at it instead, and adding an explicit system-prompt rule: a "how many"/"total" question is always answerable this way, never declined. Verified live with the exact originally-failing question plus variants, against a real seeded registry (3 invoices, 2 agreements, 1 GST document — 6 total): "how many total files do I have" → 6, "how many invoices do I have" → 3, "how many documents total" → 6, "how many agreements do I have" → 2 — all exactly right. Also re-verified "show all my invoices" still correctly uses `list_documents` (with real citations), not the new count tool, so this didn't regress the tool the model already had reaching for the right one.
- **Rate limiting**: same `20/hour` per-user limit as `/tools/*` and `/editor/chat` — one turn can trigger several Groq round trips. See [Rate limiting](#rate-limiting).
- **Verified live** against the real Supabase project and real Groq API (not mocked), using 5 realistic documents seeded under a fresh throwaway account (two agreements — one with real "exclusivity" wording, two invoices — one genuinely overdue, one not, and an overdue GST document as a deliberate distractor) — chosen deliberately over minting a token for either of the 2 pre-existing real user accounts already in the database, since that would mean accessing someone else's document content without being asked to, even read-only. All three of this phase's example queries were run against this real data and returned correct, honest, plain-text answers with accurate citations (exact request/response pairs kept for this phase's own record) — "show all active agreements" (2 real agreements, correctly excluding the invoices/GST doc), "which invoices are overdue" (exactly the 1 real overdue invoice, correctly excluding the overdue-but-not-an-invoice GST document and the not-yet-due invoice), and "find contracts mentioning exclusivity" (exactly the 1 real agreement whose text actually contains the word). All seeded documents and the throwaway account were deleted afterward.

## Analytics

Phase 28. `/analytics` (see [Navigation](#navigation)) is genuinely dynamic and AI-driven — there is no `"Invoice Analytics"` section, no `"Paid/Pending"` field, no hardcoded metric anywhere in the code. The page discovers what's actually meaningful from whatever the user's real stored data happens to contain, and would look completely different for a registry that's all Purchase Orders versus one that's all Agreements. This is the third and most safety-sensitive AI layer in the app (after the Editor assistant and the Copilot) — worth stating the core property up front:

**The model never executes a query of any kind, ever.** It can only select among 3 narrow, pre-written, parameterized Python functions (not SQL, not a query DSL, not anything it generates), and every argument to every one of those functions is re-validated against a schema summary computed fresh from real data before any database row is touched. There is no code path where a model-supplied string is interpolated into a query. This is enforced in code (`analytics.py`), not just requested in the prompt — see the verification details below.

**Step 1 — `GET /analytics/schema-summary`: "what data do we actually have."** `analytics.compute_schema_summary()` inspects the current user's own documents (scoped exactly like every other endpoint — see [Per-user document isolation](#per-user-document-isolation)) and reports, per category that actually has documents: how many documents, and which `extracted_json` keys are actually populated across those rows, with a type inferred from the real values seen (`numeric`/`string`/`boolean`/`date`/`array`/`object` — date detection reuses the same `value[:10]` ISO-parsing rule `structured_extraction.get_deadline_date()` already uses, generalized to any field). This is computed empirically from real rows every time, **not** read from `structured_extraction.SCHEMAS` — a field that's real in the schema but never actually populated in this user's data (e.g. `gst_number` on an invoice that never had one) simply doesn't appear, and a category with zero documents doesn't appear at all. Documents whose `extracted_json` is `{"parse_error": true, ...}` are excluded from field statistics entirely (that's not real structured data — see [Categories](#categories)). This schema summary **is** the whitelist every tool call below gets checked against.

**Step 2 — three real aggregation tools, not raw SQL:**

| Tool | What it does | Validation before it runs |
|---|---|---|
| `aggregate_numeric_field(category, field_name, operation)` | `sum`/`avg`/`count`/`min`/`max` over one numeric field, computed in Python over already-fetched rows | `category`+`field_name` must appear in the schema summary with type `numeric` |
| `group_and_count(category, field_name)` | Counts per distinct value of one field (e.g. Invoice by `vendor_name`, Agreement by `auto_renewal`), each group returned with both its `count` **and** its `percent` of the category total, pre-computed | field must be `numeric`/`string`/`boolean` — not `array`/`object` (e.g. `line_items`) |
| `date_field_breakdown(category, date_field_name)` | `overdue`/`due_soon`/`future`/`no_date` bucket counts, using the real `current_user.due_soon_threshold_days` — the same bucketing logic the Copilot's `get_deadline_summary` and the Tasks page already use, generalized to any date field, not just `deadline_date` | field must be `date` type |

An unlisted field, a wrong type, or an unknown category is rejected with a plain error message fed back to the model as the tool's result (`AnalyticsToolError`) — the model sees the failure and can react, but the query never ran. `field_name`/`category` are only ever used as **Python dict-key lookups** against rows already fetched by a query that only ever filters on `user_id`/`category` (both server-controlled) — never as part of a query string.

**Step 3 — `POST /analytics/generate`: the model picks what's meaningful, but every number must be real.** The schema summary is sent to Groq (`openai/gpt-oss-120b`, same model as every other AI feature) alongside the 3 tools above plus a 4th, `propose_metrics(metrics: [{label, value, format, category}])` — a structured "final answer" tool, not free text, so the output is schema-validated by Groq itself rather than parsed out of prose. The system prompt instructs the model to choose 4-8 metrics that are genuinely meaningful given what exists (never propose a field/category that isn't in the summary), call the aggregation tools to get real numbers, then call `propose_metrics` exactly once as its last action. Same agentic tool-calling loop shape as `editor_chat.py`/`copilot_chat.py` (call Groq → execute any tool calls → feed results back → repeat), kept as its own copy for the same "not enough call sites yet to justify a shared helper" reasoning given in those sections.

- **Traceability is enforced in code, not just requested in the prompt.** Every number any aggregation tool call actually returns this run is recorded into a `known_values` set, keyed by category (`aggregate_numeric_field`'s result; `group_and_count`'s per-group `count` *and* `percent`; `date_field_breakdown`'s bucket counts). When `propose_metrics` is called, `_validate_metrics()` checks every proposed `value` against that category's `known_values` (small float-rounding tolerance only, not a "close enough" fudge) — a value that doesn't match a real tool result is silently dropped, never shown to the user. If the model calls `propose_metrics` having made zero real aggregation calls, its metrics are refused (though see `fill_missing_category_metrics` below — a refusal no longer means an empty result). This is why `format: "percent"` is only ever backed by a `group_and_count` group's own pre-computed percent, never a ratio the model works out itself — there'd be nothing in `known_values` to match a self-computed percentage against.
- **Schema summary with nothing usable → no Groq call at all.** If the user has zero documents with populated `extracted_json`, `generate_analytics()` returns an empty result immediately rather than spending an API call finding that out.
- **Every category with real documents is guaranteed at least one metric — `fill_missing_category_metrics()`, a deterministic code-level backstop, not just a prompted request.** See "Bug fixes" below for the real, live-reproduced failure mode this closes: the model's own tool-calling exploration is not reliably deterministic run-to-run, so a category can otherwise go entirely unmentioned in the final proposal even though it has real, populated data. After `_validate_metrics()` runs, `fill_missing_category_metrics()` checks every category in the schema summary against the categories actually present in the validated metrics and, for any that are missing (and have `document_count > 0`), appends a `{"{category} documents", format: "count", value: document_count}` metric — using `document_count`, already known from the schema summary, so this never costs an extra Groq call or DB query. Applied at **every** exit point of `generate_analytics()`'s loop (a clean proposal, a zero-tool-calls refusal, and running out of `MAX_TOOL_ROUNDS`), so none of them can produce fewer categories than the schema summary actually has — only a schema summary with *no* categories at all (an empty registry) still short-circuits to a genuinely empty result.

**Caching**: `analytics_cache` (`TTLCache`, `analytics_router.py`), **600 seconds** — meaningfully longer than `documents_cache`/`deadlines_cache`'s 60s (see [Caching](#caching)) because this is genuinely more expensive to compute: several sequential Groq round trips per generation (measured live between ~7s and ~48s depending on how many tool-calling rounds the model needs), not one cheap DB query. Keyed by user id, same reasoning as every other cache in this app. `POST /analytics/generate?force=true` (the frontend's "Regenerate" button) bypasses the cache and recomputes; a failed generation is deliberately **not** cached, so a transient Groq hiccup doesn't lock the user out of a real result for the full TTL — the next request just tries again. This includes the case where `generate_analytics()` raises entirely (e.g. a real Groq outage/rate limit) — `analytics_router.py`'s top-level `except` still returns `fill_missing_category_metrics([], schema_summary)` (real per-category document counts) rather than an empty result, but that fallback response is never written to `analytics_cache`, so the very next request tries Groq fresh rather than being stuck showing only document counts for the rest of the 10-minute window.

**Frontend** (`app/(app)/analytics/page.tsx`) — no hardcoded section or metric names anywhere in the component. Fetches `POST /analytics/generate` on mount, groups whatever `metrics` the response contains by their own `category` value (a `Map` built from the response, not a fixed list — a category with no metrics this run just doesn't get a section), and renders each as a stat tile in the same visual pattern (`Card`, uppercase label, big serif tabular-nums value) already used on the Documents page and Home. `format` drives display: `currency` → `₹X,XX,XXX.XX` (via `Intl.NumberFormat("en-IN", {style: "currency", currency: "INR"})` — see "Bug fixes" below), `percent` → `XX.X%`, `count` → a plain number. A "Regenerate" button calls the same endpoint with `force=true`; a small caption shows when it was generated and whether this response was `(cached)`. Empty state (no metrics) reads "Not enough data yet to generate analytics" rather than showing an empty grid or a fabricated placeholder.

**Bug fixes (found on real, live data — not synthetic test fixtures):**

- **Currency was hardcoded to `$`, even though every real document in this app so far is Indian-denominated.** `formatMetricValue()` literally prepended a `"$"` string. Fixed to `Intl.NumberFormat("en-IN", { style: "currency", currency: "INR" })`, which also gives correct Indian digit grouping (e.g. `₹5,40,000.00`) for free. **Deliberately defaults to INR unconditionally rather than detecting currency per-document** — a real tradeoff, stated plainly: a registry mixing Indian and non-Indian invoices would still sum/average their amounts together regardless of what symbol is shown, since `analytics.py`'s aggregation tools have no notion of currency at all (that was already true before this fix). Genuine multi-currency support would mean grouping aggregates by currency before summing them, not just picking a different symbol — a materially bigger change than this bug fix's scope, and not yet justified: every real document currently in this app (the KGraph invoice, the OAM purchase order, the Haldiram agreement) is Indian. Revisit this default if a genuinely non-Indian document is ever added to a real registry.
- **A real Agreement document (`Haldiram_KGraph_SignedContractFinal.pdf`) never appeared in Analytics, despite existing and having populated fields.** Root-caused by directly reproducing the exact page, not guessing:
  1. Confirmed directly against the real database: the document's `category` is genuinely `"Agreement"` and its `extracted_json` is genuinely populated (`expiry_date`, `effective_date`, `auto_renewal`, `party_names`, `key_obligations`).
  2. Called `compute_schema_summary()` directly for the real user — it **correctly** reported an `Agreement` category entry with `auto_renewal` (boolean), `effective_date`/`expiry_date` (date), both genuinely aggregation-eligible (`group_and_count` accepts boolean; `date_field_breakdown` accepts date). The schema summary was never the problem.
  3. Traced `generate_analytics()`'s real, live tool-calling loop step by step against the real schema summary (not mocked) — the model **did** sometimes call `group_and_count`/`date_field_breakdown` on Agreement and propose real Agreement metrics. The bug was intermittent, not constant, which ruled out a hard-coded gap.
  4. Ran the real function **five times back-to-back** against the identical real schema summary (`temperature=0` notwithstanding): **4 of 5 runs omitted an entire category from the final proposal** — most of those runs dropped Purchase Order, one dropped Agreement, matching what the user actually saw. The model was spending its tool-call budget on one or two categories with richer/more "interesting" numeric fields and simply never getting to (or choosing to skip) a category whose only usable fields were sparser (a boolean and two dates, in Agreement's case) before calling `propose_metrics`.
  5. **Root cause: the agentic loop's per-category coverage was never actually guaranteed — only prompted for, and prompting alone was not reliable.** Fixed with a real, code-level guarantee (`fill_missing_category_metrics()`, described above) plus a strengthened system prompt (explicitly stating full coverage is a hard requirement, not a preference) and `MAX_TOOL_ROUNDS` raised from 6 to 8 (more headroom to reach every category on its own, though the code-level backstop is the actual guarantee, not this).
  6. **A related gap found while verifying the fix live**: this session's own repeated testing had, by this point, genuinely exhausted Groq's real daily token quota (a live `429` — confirmed from the real error body, not simulated). This surfaced a second bug: `analytics_router.py`'s top-level exception handler returned a bare empty result on any total `generate_analytics()` failure, with no fallback at all — fixed the same way, via `fill_missing_category_metrics([], schema_summary)` in that `except` block too (never cached — see Caching above).
  - **Verified live, both fixes together, against the real user's real registry, with Groq's real quota still exhausted at verification time**: replicated the router's exact logic directly — `generate_analytics()` raised `RateLimitError` (confirmed real, live), the `except` fallback engaged, and the response correctly included all three real categories — `Agreement` (`"Agreement documents": 1`), `Invoice`, and `Purchase Order` — where before this fix the same real failure would have produced an empty result. Also verified twice more, at HTTP level against a freshly-started server, with synthetic 3-category data, confirming the full request/cache/response path.
  - **Tests**: `test_generate_fills_in_a_category_the_model_never_explored` (seeds Invoice + Agreement, mocks the model to touch only Invoice, asserts Agreement still appears via its document-count fallback) and `test_generate_falls_back_on_total_groq_failure_and_is_not_cached` (mocks a total Groq failure, asserts the fallback response is real and is never cached — a follow-up call picks up a fresh, real result immediately).

**Verified live** against the real Groq API (not mocked), using 9 realistic documents seeded under a fresh throwaway account — 4 Invoices (`amount`/`vendor_name`/`due_date`), 3 Agreements (`auto_renewal`/`expiry_date`/`party_names` — deliberately including the array field `party_names`, to confirm it never gets used for aggregation), and 2 GST Documents (`tax_amount`/`filing_date`/`gstin`) — with **no payment-status field anywhere**, to test the negative case the phase itself called out. `GET /analytics/schema-summary` correctly reported exactly the real populated fields (including `renewal_notice_period` at `populated_count: 2`, not 3, since one Agreement had it `null`) and nothing else — no invented field, no `parse_error` row counted. `POST /analytics/generate` was run twice (a cold call, then a forced regeneration) and produced two different-but-equally-valid sets of real metrics, every one hand-verified against the seeded data:
- "Average invoice amount": $1,830.19 = (4250.00 + 1800.50 + 950.25 + 320.00) / 4 ✓
- "Total invoice amount": $7,320.75 = sum of the same 4 ✓
- "Overdue invoices": 2, "Invoices due soon": 2 — matched the 2 invoices with a past `due_date` and the 2 with a `due_date` within the threshold ✓
- "Agreements set to auto-renew" / "not set to auto-renew": 66.7% / 33.3% = 2/3 and 1/3 of the 3 seeded agreements ✓

No `paid`/`pending`-style metric was ever proposed, in either run — there was no such field for the model to find. Caching was verified directly: a second immediate call returned `cached: true` with identical metrics and made no new Groq calls (confirmed via a call-counting mock in `test_analytics.py`, and observed live as a ~7s call followed by a near-instant one); `?force=true` bypassed it and regenerated for real. ## GROQ_API_KEY usage

`backend/classification.py` calls the Groq API via the official `groq` Python client, authenticated with `GROQ_API_KEY`:

```python
from groq import Groq

client = Groq(api_key=GROQ_API_KEY)

response = client.chat.completions.create(
    model="openai/gpt-oss-120b",
    messages=[
        {"role": "system", "content": "You are a document classifier. ... Return a single JSON object with exactly two keys: \"category\" (one of: Agreement, Invoice, GST Document, Bank Statement, Purchase Order, Other) and \"reasoning\" (one short sentence explaining why)."},
        {"role": "user", "content": raw_text[:4000]},
    ],
    temperature=0,
    max_tokens=300,
    reasoning_effort="low",
    response_format={"type": "json_object"},
)
category, reasoning = parse_classification(response.choices[0].message.content)
```

On a 429 (`groq.RateLimitError`), the call is retried with exponential backoff — sleep `2**attempt` seconds (1s, 2s, 4s) — up to 3 retries (4 attempts total) before giving up and letting the error propagate to `process_document()`, which records it as `classification_failed`.

**Reasoning-model gotcha**: `openai/gpt-oss-120b` (and other reasoning-style models on Groq) spend part of the token budget on an internal `reasoning` field before writing `content` — that reasoning usage counts against `max_tokens`. The original `max_tokens=20` (copied over from the old non-reasoning `llama-3.3-70b-versatile` model) was too small: the model would hit the cap mid-reasoning (`finish_reason: "length"`) and return `content: ""`, which `parse_classification()` then silently defaulted to `"Other"` — a real invoice got misclassified with no error anywhere. Fixed by raising `max_tokens` (300 for classification, 800 already was enough for structured extraction) and passing `reasoning_effort="low"` to keep the reasoning phase short. If you swap in a different reasoning model again, re-check this — an empty/truncated Groq response fails silently into a valid-looking category (`Other`, with a synthesized "couldn't be parsed" reasoning string) or an unparseable JSON response, not an exception, so it won't show up as `*_failed` in `status`.

`backend/structured_extraction.py` uses the same client and retry logic, but adds `response_format={"type": "json_object"}` to make Groq return JSON, and puts the target schema directly in the system prompt:

```python
response = client.chat.completions.create(
    model="openai/gpt-oss-120b",
    messages=[
        {"role": "system", "content": (
            'You are a document data extractor for Invoice documents. Extract the following '
            'fields and return them as a single JSON object with exactly these keys:\n'
            '{\n  "vendor_name": string or null\n  "invoice_number": string or null\n  '
            '"invoice_date": ISO date or null\n  "due_date": ISO date or null\n  '
            '"amount": number or null\n  "gst_number": string or null\n}\n'
            'Use null for any field you cannot find. Return ONLY the JSON object.'
        )},
        {"role": "user", "content": raw_text[:4000]},
    ],
    temperature=0,
    max_tokens=800,
    response_format={"type": "json_object"},
)
extracted_json = json.loads(response.choices[0].message.content)
```

If `json.loads` fails, it's retried once with the same messages plus a line telling the model its previous reply wasn't valid JSON; if that also fails, the raw text is stored as `{"parse_error": true, "raw_response": "..."}` instead of raising.

## Deployment (Render)

[render.yaml](render.yaml) is a Render [Blueprint](https://render.com/docs/blueprint-spec) defining both services — connect the repo in the Render dashboard via "New +" → "Blueprint" and it reads this file automatically. No custom domain is set up yet. See [CI/CD](#cicd) for how this fits together with GitHub Actions — the short version: GitHub Actions only ever runs checks, Render's own git-push auto-deploy (below) is still the entire deploy mechanism, unchanged.

- **`documentos-ai-backend`** — `env: docker`, built from [backend/Dockerfile](backend/Dockerfile) (installs `tesseract-ocr`, see [System dependencies](#system-dependencies)), free plan, health check at `/health`. Its real Render hostname is **not** the plain `documentos-ai-backend.onrender.com` — that name collided with an unrelated existing service, so Render assigned a suffixed hostname instead (visible in `NEXT_PUBLIC_API_URL`'s actual configured value, or by grepping the deployed frontend's own JS bundle for `onrender.com`, since it's inlined at build time). Don't assume the unsuffixed name when scripting against production — verify it first.
- **`documentos-ai-frontend`** — `env: node`, root `frontend/`, `npm install && npm run build`, started with `next start -p $PORT` (Render assigns the port via `$PORT`; `next start`'s default of `3000` doesn't apply on Render).

**Environment variables to set in the Render dashboard** — `render.yaml` declares each with `sync: false`, which tells Render the key exists but the value must be entered manually per environment (dashboard → service → Environment) rather than committed to the repo:

| Service | Variable |
|---|---|
| `documentos-ai-backend` | `GROQ_API_KEY`, `SUPABASE_DB_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (same purposes as in [Environment variables](#environment-variables) above) |
| `documentos-ai-frontend` | `NEXT_PUBLIC_API_URL` — set this to the backend service's real Render URL (see the suffixed-hostname note above), not `localhost` |

**Migrations now run automatically on every deploy — "migrate on boot".** `backend/Dockerfile`'s `CMD` runs `alembic upgrade head && uvicorn ...`: every container start (every deploy, and every free-tier cold-start wake from idle) applies any pending migration before the app starts serving traffic, and a failed migration stops the container from starting at all rather than serving requests against a stale schema. This was **not** the original design — `render.yaml` has no `preDeployCommand` (Render's free plan doesn't support it at all; it's a paid-plan-only feature — confirmed directly, not assumed), so this project originally required a human to remember to run `alembic upgrade head` against `SUPABASE_DB_URL` manually after every deploy that added a migration. That manual step was skipped once for real: migration `0018_add_source_to_documents` (see [Document source separation](#document-source-separation)) shipped in app code while production's database was still missing the `source` column, causing real 500s on `GET /documents` and `POST /documents/upload` in production until the migration was applied by hand and this Dockerfile fix went in. Verified live against the real production database and the real deployed backend: `alembic current` showed production stuck at `0017` (one migration behind head) while `generated_from_template_id` from the earlier `0015` migration was already present — the gap was exactly and only the one unapplied migration; after applying it, the backfill was confirmed correct (all 3 pre-existing rows got `source='upload'`, zero NULLs, zero disagreement with `generated_from_template_id`), and a real register → upload → poll → list → delete-account round trip against the live backend succeeded end to end with no 500s.

### Second frontend deployment (Vercel)

The frontend is genuinely deployed **twice**, to two different platforms, both currently live: Render's own `documentos-ai-frontend` service (above) **and** a separate Vercel deployment at `https://document-os-ai.vercel.app`. This isn't documented anywhere in `render.yaml` (Vercel deployments aren't a Render Blueprint concept at all) — it exists as its own independent Vercel project, presumably connected to the same GitHub repo directly through Vercel's own git integration, deploying on the same pushes to `main`.

**Verified live, not assumed**: both frontends are currently up and both point at the exact same backend — confirmed by fetching each deployment's own built JS and grepping for its build-time-inlined `NEXT_PUBLIC_API_URL` (both resolve to `documentos-ai-backend-zif7.onrender.com`, the real suffixed hostname noted above). A direct CORS preflight (`OPTIONS /auth/login`) against that backend with each frontend's origin got back a matching `access-control-allow-origin` for both — meaning the backend's `ALLOWED_ORIGINS` env var (see [Security](#security)) is currently configured with **both** origins, not just one. Neither deployment is retired; both are real, working, independent front doors onto the same backend/database.

**What this means for future changes**: `ALLOWED_ORIGINS` (backend, Render dashboard) must keep listing both `https://documentos-ai-frontend.onrender.com` and `https://document-os-ai.vercel.app` — dropping either from that comma-separated list silently breaks that one frontend's ability to call the API (CORS failures, not an obvious server error). Conversely, `NEXT_PUBLIC_API_URL` is set independently per platform (Render dashboard env var for the Render frontend; Vercel's own project environment variables for the Vercel one) — if the backend's URL ever changes (a new Render service, a custom domain), **both** need updating, not just one. If one of these two frontend deployments is ever deliberately retired, update this note (and prune its origin from `ALLOWED_ORIGINS`) rather than leaving a stale allowed-origin around indefinitely.

## Testing

### Testing policy

- While iterating: run only the tests relevant to the change (the specific test file, or `pytest -k <keyword>`). Don't run the full suite after every edit.
- Run the full backend suite once, at the end of a phase, only if the change touches shared code: models, migrations, auth, the documents list/detail endpoints, storage helpers, or rate limiting.
- UI-only and copy/styling changes: no backend tests.
- If a targeted run fails, use `pytest --lf` to re-run only the failures instead of everything.

Two suites, both real (run against a real Postgres and a real browser, not stubbed frameworks), neither touching the real Supabase project.

**Backend — pytest** (`backend/tests/`):

- `test_auth.py` — register (success, duplicate email, all three password-strength rejection cases), login (success, wrong password, nonexistent user — same generic error either way), `GET /auth/me` (missing/garbage token vs. valid), `PATCH /auth/profile` (name/email update, duplicate-email rejection, keeping your own current email), and the `/auth/login` rate limit (5/minute — see [Rate limiting](#rate-limiting)).
- `test_upload_pipeline.py` — the full extract → classify → structure pipeline through the real `POST /documents/upload` endpoint, with Supabase Storage and every Groq call mocked via `monkeypatch` (see below for why): a happy path (Invoice, asserts `extracted_json`/`deadline_date`/`classification_reasoning` all come through correctly — via a `GET /documents/{id}` poll, since the upload response itself is only ever the immediate `"uploaded"` state, see [Background processing](#background-processing)), a classification-failure path (asserts `error_message` is the sanitized generic string, never the raw mocked exception text — a direct regression test for the [Security](#security) section's error-message fix), a Bank Statement upload (asserts structured extraction is skipped, per [Document processing](#document-processing)), and the file-validation/auth rejection cases (magic-byte mismatch, empty file, unsupported extension, no token).
- `test_deadlines.py` — seeds documents directly via a DB session with specific `deadline_date`s, then asserts on `GET /documents/deadlines`: excludes null-deadline documents, `urgency=overdue`/`due-soon` filtering, ascending sort order, the 400 on an invalid `urgency` value, and that the response omits `raw_text` (see [Performance notes](#performance-notes)).

## CI/CD

GitHub Actions, [.github/workflows/ci.yml](.github/workflows/ci.yml) — **checks only, never deploys**. Render's existing git-based auto-deploy (see [Deployment](#deployment-render)) remains the entire deploy mechanism; this workflow doesn't touch it.

- **Triggers**: every pull request into `main`, and every push to `main` (the latter as a safety net/confirmation after merge, not a deploy trigger).
- **`backend-tests`**: spins up a `postgres:16-alpine` [service container](https://docs.github.com/en/actions/using-containerized-services/about-service-containers) (the same disposable-test-database approach as local `test.sh`/`test.ps1`, see [Testing](#testing)), installs `backend/requirements-dev.txt`, runs `pytest`.
- **`frontend-checks`**: `npm ci`, then `tsc --noEmit`, `npm run lint`, and `npm run build` — the same three checks this project's own workflow has always run manually before considering frontend work done (see e.g. the verification steps described throughout this file), now enforced automatically instead of relying on remembering to run them.
- **`frontend-e2e`**: installs Playwright's Chromium browser (`npx playwright install --with-deps chromium`) and runs the e2e suite, which builds and starts a production build itself via `playwright.config.ts`'s `webServer` (see [Testing](#testing) for why it's a production build, not `npm run dev`). No live backend is needed in this job — see [Testing](#testing)'s note on `page.route()` mocking. This means the frontend gets built twice across the two frontend jobs (once in `frontend-checks`, again here) since each job runs in its own fresh checkout with nothing shared between them — a known minor inefficiency, not a correctness issue; worth revisiting (e.g. building once and passing the artifact between jobs) only if CI time actually becomes a problem.
- **The full pipeline, end to end**: PR opened → all three jobs above run → (once branch protection is turned on, see below) all three must pass before the PR can be merged → merge to `main` → the same three jobs run again on `main` as a safety net → **independently of GitHub Actions**, Render's git integration notices the push to `main` and redeploys both services automatically, exactly as it did before this phase. Worth being explicit about the gap this leaves: Render's auto-deploy is not itself gated on this workflow passing — nothing currently *stops* a merge-to-main (and therefore a Render deploy) from going out if the post-merge run happens to fail. The only thing that actually gates a bad change from reaching `main` at all is requiring the PR-time checks to pass *before* merge, which is a branch protection setting, not something expressible in a workflow file — see below.
- **Branch protection (not committable — a manual GitHub repo setting)**: GitHub Actions workflows can report pass/fail, but nothing about "block the merge button until checks pass" lives in code; it has to be turned on once, by hand, in the repo's own settings. Recommended: **Settings → Branches → Add branch protection rule** for `main`, enable **"Require a pull request before merging"** and **"Require status checks to pass before merging"**, then select the three job names above (`backend-tests`, `frontend-checks`, `frontend-e2e`) as required checks. Optionally also **"Require branches to be up to date before merging"** so a PR can't merge against a stale base that later conflicts with what else landed on `main`.
- **Not independently verified against a real GitHub Actions run** — this local project isn't a git repository (no remote to push to and trigger a real run against), unlike every other change in this file, which was checked against real running infrastructure before being documented. What *was* verified: the YAML parses correctly (via a Python YAML parser), every command the workflow runs (`pytest`, `npx tsc --noEmit`, `npm run lint`, `npm run build`, `npx playwright install --with-deps chromium`, `npx playwright test`) was run successfully in this exact form against this exact codebase locally, and the referenced files (`backend/requirements-dev.txt`, `frontend/package-lock.json`) exist. Re-check the first real run on GitHub once this repo has a remote — Ubuntu's `ubuntu-latest` runner is a different environment than this Windows dev machine, most likely to bite on the Playwright browser's system dependencies (`--with-deps` should cover it, but that flag itself wasn't exercised here since Chromium was already present in this local Windows environment via a plain `playwright install chromium`).

## Structured logging

Both the backend's own logging and the ad-hoc `logging.basicConfig(...)` line from [Phase 11's security work](#security) were replaced with real structured logging (`backend/logging_config.py`), configured once at import time in `main.py`.

- **Format**: one JSON object per line (`JSONFormatter`) — `timestamp`, `level`, `logger`, `message`, `request_id`, plus any extra fields a call site passed via `logger.info(..., extra={...})`, plus `exception` (full traceback) when logged via `logger.exception(...)`. Machine-parseable — greppable by `request_id`, ready to feed into a log aggregator later — instead of the free-text line `logging.basicConfig` produced before.
- **Request IDs**: `main.py`'s `request_context_middleware` generates a UUID per request, stores it in a `contextvars.ContextVar` (`logging_config.request_id_var`), and returns it as an `X-Request-ID` response header. `RequestIdFilter` reads that contextvar into every `LogRecord`, so every log line emitted while handling a request — including calls several functions deep, e.g. inside `processing.py` — carries the same id, without threading a `request_id` parameter through every function signature by hand. Contextvars propagate correctly through `await`/async code and through FastAPI's threadpool-offloaded sync endpoints (`anyio.to_thread.run_sync` copies the current context into the worker thread), so this works for both `def` and `async def` path operations.
- **One structured line per request**: `request_context_middleware` itself logs `method`/`path`/`status_code`/`duration_ms` after every request completes. `uvicorn.access`'s own differently-shaped access log is set to `WARNING` in `configure_logging()` to avoid a second, redundant line per request. (Uvicorn's own startup/lifecycle banner lines — "Started server process", "Uvicorn running on..." — keep uvicorn's own plain-text format; those come from uvicorn's own loggers before/outside `main.py`'s reconfiguration and aren't part of the application's own request handling, so there's nothing to gain restructuring them.)
- **Unhandled exceptions**: an exception that escapes a path operation entirely (not one of the app's own `except Exception: ... HTTPException(...)` handlers — see [Security](#security)) is caught by the middleware, logged via `logger.exception(...)` (full traceback, still tagged with the request's `request_id`), and re-raised so FastAPI's normal 500 handling still applies — verified live by adding a route that deliberately raises: the exception was logged with a full structured traceback and the app still returned a clean 500, it didn't crash the process.
- **Never logs sensitive data**: no logger call in this codebase passes a raw request body, a password, a token, or a document's `raw_text` — see the Security section's note on `error_message` already being sanitized before it ever reaches a log call, and `processing.py`'s logger calls only ever pass a document id.
- **`scripts/reclassify_other_documents.py` is deliberately exempted** — it's a one-off CLI script a developer runs and reads directly from a terminal, not part of the running API service; its `print()` calls are its actual intended UI (progress/summary output for a human watching it run), and converting them to JSON log lines would make the script worse at its one job, not better.

## Error tracking (Sentry)

Both backend and frontend integrate Sentry (free tier) for unhandled-exception tracking with request/user context — both are **no-ops until a DSN is configured** (`SENTRY_DSN` / `NEXT_PUBLIC_SENTRY_DSN`, see [Environment variables](#environment-variables)), so the app behaves identically with or without a Sentry project set up. No Sentry project/account was created as part of this work — that's a manual step (see below).

**Backend** (`error_tracking.py`, `sentry-sdk[fastapi]`):

- `init_error_tracking()` (called once in `main.py`, right after `configure_logging()`) calls `sentry_sdk.init()` only `if SENTRY_DSN` — every other `sentry_sdk.*` call in the app (`set_user`, `set_tag`, the SDK's own auto-capture) is a safe no-op when `init()` was never called at all, verified directly (calling `set_user`/`set_tag`/`capture_exception` with no prior `init()` call raises nothing).
- **Context attached to every event**: `request_context_middleware` tags each event with the request's `request_id` (`sentry_sdk.set_tag`); `auth.get_current_user()` sets the authenticated user (`sentry_sdk.set_user({"id": str(user.id)})`, email deliberately left out) once a request resolves a valid token. Request path/method come from Sentry's own FastAPI/Starlette auto-instrumentation, which is active as soon as `sentry-sdk[fastapi]` is installed and `init()` runs — confirmed live (see below) by the traceback of a captured exception passing through `sentry_sdk/integrations/{fastapi,starlette}.py`.
- **Never sends sensitive data**: `send_default_pii=False` (explicit, not just relying on the default) — no automatic IP/cookie/request-body capture. `_before_send` (`error_tracking.py`) additionally scrubs any request headers/data or `extra` context that does get attached — redacting `Authorization` headers and any field named `password`/`current_password`/`new_password`/`token`/`access_token`/`raw_text` — as defense in depth on top of the app already never handing those fields to Sentry (or to a logger) in the first place.
- **Verified live** (using a syntactically valid but fake DSN, since no real Sentry project exists yet): the server starts and serves `/health` immediately (init doesn't block on a network call); a deliberately-raised unhandled exception was logged with a full traceback *and* Sentry reported "attempting to send 2 pending events" with a bounded 2-second flush timeout on shutdown — it never hangs waiting on an unreachable/fake ingest host, and the request still returned a clean 500.

**Frontend** (`instrumentation.ts`, `instrumentation-client.ts`, `app/global-error.tsx`, `@sentry/nextjs`):

- This app is on Next.js 14.2.15, and `@sentry/nextjs` v10's **current** setup convention (confirmed by reading the installed package's own build tooling, not assumed) is: `Sentry.init()` lives inside `instrumentation.ts`'s exported `register()` function (the build tooling explicitly warns — and fails the build — if it finds `Sentry.init` in a separate `sentry.server.config.ts` instead), plus an exported `onRequestError = Sentry.captureRequestError` for server-side/React-Server-Component errors; client-side init lives in `instrumentation-client.ts` (the modern replacement for `sentry.client.config.ts`), which must also export `onRouterTransitionStart = Sentry.captureRouterTransitionStart` for navigation instrumentation or the build warns. `next.config.mjs` is wrapped with `withSentryConfig` (imported from `@sentry/nextjs/config`, not the deprecated `@sentry/nextjs` top-level export) and sets `experimental.instrumentationHook: true`, which Next.js 14 (unlike 15+) needs explicitly for those hooks to run at all.
- `app/global-error.tsx` (new — nothing like it existed before) captures React rendering errors that escape the root layout itself via `Sentry.captureException` in a `useEffect`, styled with this app's own design tokens rather than Sentry's generic fallback UI.
- `lib/sentry-scrub.ts`'s `scrubSensitiveData` is the same scrubbing logic as the backend's `_before_send` (same key list, same reasoning), shared by both `instrumentation.ts` and `instrumentation-client.ts`. `sendDefaultPii: false` is set explicitly on both, matching the backend.
- **Verified live**: `npm run build` succeeds both with no DSN set (the default — everything no-ops) and with a fake DSN set (confirming the init path itself doesn't break the build); with the fake DSN, the production server was started and `/login` loaded in a real headless browser with **zero console/page errors** — `Sentry.init()` runs client-side without throwing. The full Playwright e2e suite (see [Testing](#testing)) was re-run afterward with no DSN set (its default) and still passes — the instrumentation adds no regression to normal app behavior. One real, unrelated flake surfaced during this verification: a completely cold `.next` cache under 5 parallel Playwright workers occasionally exceeded the default 5s assertion timeout (this app's dev-mode cold-compile cost, see [Performance notes](#performance-notes), not a Sentry issue) — fixed by raising `playwright.config.ts`'s `expect.timeout` to 10s, then re-verified clean from a cold cache.
- Sentry's client bundle adds real weight — shared First Load JS went from ~87KB to ~145KB after installing `@sentry/nextjs`, visible in `npm run build`'s own output. Expected and accepted for the error-visibility tradeoff at this app's scale.

**What's deliberately not configured, and why**:

- **Performance tracing / `tracesSampleRate`**: set to `0` on both sides. The ask was error tracking, not APM — leaving this off keeps Sentry's free-tier event quota focused on actual errors instead of being consumed by performance transactions nobody asked for.
- **Source map upload** (`SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN`, for readable stack traces on minified production JS): not set up — this needs a real Sentry project and auth token to exist first (see below), and `next.config.mjs`'s `withSentryConfig` call already has `silent: true` so it doesn't warn/fail the build over their absence. Worth doing once a real project exists, so a captured frontend error's stack trace points at real source lines instead of a minified bundle.

**The one remaining manual step** (can't be done from here — needs an interactive account/browser): create a free Sentry project (Settings → Projects → Create Project, platform: Python/FastAPI for one project, Next.js for another, or a single project covering both), copy its DSN into `SENTRY_DSN` (backend `.env` / Render dashboard) and `NEXT_PUBLIC_SENTRY_DSN` (frontend — Render dashboard, since it's a build-time-inlined `NEXT_PUBLIC_` var), and set `ENVIRONMENT`/`NEXT_PUBLIC_SENTRY_ENVIRONMENT` to `production` there. Everything else (scrubbing, context, the instrumentation files themselves) is already wired up and ready — flipping those env vars on is the only step left.

## Monitoring

Configuration + documentation only — no code changes for this phase, per how it was scoped.

**Uptime monitoring** (not yet set up — a manual step, same reasoning as the Sentry project above: needs an interactive account, can't be created from here): use [UptimeRobot](https://uptimerobot.com)'s free tier (or an equivalent — Better Uptime and Pulsetic both also have workable free tiers).

- **Monitor type**: HTTP(s). **URL**: the deployed backend's `/health` endpoint (e.g. `https://documentos-ai-backend.onrender.com/health`) — deliberately not auth-protected for exactly this reason (see [API endpoints](#api-endpoints)). **Interval**: 5 minutes (UptimeRobot's free-tier minimum). **Alert contact**: email.
- **Real side effect worth knowing about**: a monitor pinging every 5 minutes keeps Render's free-tier backend from ever going idle long enough to spin down (the 15-minute-inactivity cold-start behavior documented in [Known free-tier limits](#known-free-tier-limits-to-watch)) — so setting this up doesn't just add alerting, it likely eliminates the cold-start problem for anyone hitting the app during business hours. The tradeoff: Render's free tier has a monthly instance-hour budget, and a service that never sleeps uses more of it than one that spins down between uses — worth keeping an eye on if usage patterns change later.
- Once configured, a real outage (Render deploy failure, Supabase project down, the process crashing) surfaces as an email within one 5-minute check cycle instead of "someone notices the app is broken."

**Render's built-in metrics** (already exists, no setup needed — just needs someone to actually look at it, which is the "confirm it's being checked" part of this phase): dashboard → the service (`documentos-ai-backend` or `documentos-ai-frontend`) → **Metrics** tab. Shows CPU%, memory, and HTTP request/response-time graphs over a selectable time window.

- **Normal, for this app at its current (POC) scale**: mostly-idle CPU and flat low memory between requests. `POST /documents/upload` itself should now be fast (file validation + a Storage upload, no OCR/Groq wait — see [Background processing](#background-processing)); the actual extract → classify → structure pipeline still costs real CPU/time (OCR plus up to two Groq round-trips), but shows up as a brief spike on a background worker thread shortly *after* the upload request completes, not as a slow upload response. Every list/auth endpoint (`GET /documents`, `/documents/deadlines`, `/auth/*`) should stay fast (tens of milliseconds) per the [Performance notes](#performance-notes) and [Caching](#caching) work — those aren't expected to show up as slow on this graph at all.
- **Concerning, worth investigating**: memory climbing steadily over hours/days without dropping back down between requests (a leak — nothing currently retains state across requests, so this would be unexpected); response times on the *fast* endpoints (list/auth) creeping up, which would point back at the database rather than at Groq/OCR; CPU pegged near 100% outside of an active upload; or a cluster of 5xx responses on the graph lining up with a burst of events in Sentry (once configured, see above) — that correlation is the fastest way to go from "the metrics graph looks weird" to "here's the actual stack trace."
- Free-tier services also show a flat drop to zero traffic followed by a slow first response after any idle period — that's the cold-start behavior in [Known free-tier limits](#known-free-tier-limits-to-watch), not an incident, whether or not the uptime monitor above is keeping it mostly at bay.

## Caching

An in-process, thread-safe TTL cache (`backend/cache.py`'s `TTLCache` — a `dict` + a lock + `time.monotonic()` expiry, nothing fancier) for reads that are hit often and don't need to be fresh to the second. **Redis is the natural next step** if this app ever runs with more than one backend process (`uvicorn --workers`, or multiple Render instances) — an in-process cache like this one is invisible to every process but its own, which is fine today (a single process, no `--workers` — see [Rate limiting](#rate-limiting)'s identical reasoning for `slowapi`'s own storage) and wrong the moment that changes.

**What's cached, and for how long**:

| Cached | TTL | Key |
|---|---|---|
| `GET /documents` (`documents_cache`) | 60s | `(user id, category, upload_date_from, upload_date_to)` |
| `GET /documents/deadlines` (`deadlines_cache`) | 60s | `(user id, urgency)` |
| `GET /documents/{id}/download-url` (`signed_url_cache`) | 270s | `document id` |
| `POST /analytics/generate` (`analytics_cache`, `analytics_router.py`) | 600s | `user id` |

- **Stat-tile counts (Documents page and Home) aren't a separate cache entry** — they're computed client-side from the same `GET /documents` response the Documents table already renders (see [Frontend pages](#frontend-pages)), not fetched separately, so caching that one endpoint covers both. There's no dedicated stats endpoint to add a second cache to.
- **Keyed by user id, and it matters now**: originally added when every user still saw the same document set (no ownership existed yet), on the reasoning that it'd cost one tuple element now and stay correct later. [Per-user document isolation](#per-user-document-isolation) is that "later" — the underlying queries are genuinely per-user now, so this key is load-bearing: without it, one user's cached list would leak into another user's request for the same route. Directly regression-tested (`test_isolation.py::test_each_users_cache_entry_is_independent`) and verified live against the real deployment.
- **The signed-URL TTL is 270s, not the full 300s `DOWNLOAD_URL_EXPIRES_SECONDS`** — a URL served right before its cache entry would've expired anyway should still have a reasonable amount of real validity left when the client gets it, not expire moments later.
- **`analytics_cache`'s 600s TTL is deliberately the longest cache in this app** — see [Analytics](#analytics) for why (several sequential Groq round trips per generation, not one cheap query) and for how `?force=true` (the "Regenerate" button) bypasses it, and why a failed generation is never cached.
- **Cached values are already-serialized `DocumentListOut` Pydantic models, not raw SQLAlchemy `Document` objects** — caching the ORM objects directly would mean holding onto rows from a DB session that's closed by the time a later request reads them from cache; validating to the response model before caching sidesteps that entirely.
- **Invalidation**: `invalidate_document_list_caches()` (moved into `cache.py` itself in Phase 32, alongside the two cache instances — see below) clears both `documents_cache` and `deadlines_cache` outright — *every* user's entries, not just the acting user's — after anything that changes what those endpoints would return: `POST /documents/upload` (both when the row is first created *and* again when the background pipeline finishes, see [Background processing](#background-processing) — otherwise a just-completed upload's category/status could sit stale in the list cache for up to 60s even though `GET /documents/{id}` already shows the real state), `DELETE /documents/{id}`, `POST /documents/{id}/reprocess`, and — Phase 32 — `POST /templates/learn-from-sample` (the sample it saves is a real document) and `POST /templates/{id}/generate` (a real, newly-generated document). Clearing everyone's cache over one user's write is broader than strictly necessary now that documents are per-user, but writes are rare relative to reads, so the simplicity still wins over a more surgical per-user invalidation.
- **Why `documents_cache`/`deadlines_cache`/`invalidate_document_list_caches()` live in `cache.py`, not `main.py`** (moved there in Phase 32): `templates_router.py` also needs to invalidate these two caches (see above), and `main.py` already imports `templates_router` — `templates_router` importing back from `main.py` for these would be a circular import. `main.py` still defines and owns `signed_url_cache` locally, since nothing outside `main.py` needs to invalidate that one. The signed-URL cache is *not* invalidated on delete — a signed URL's real validity is tied to the underlying Storage object's existence, not to this cache; deleting the object makes any previously-issued URL for it 404 regardless of whether this cache remembers it. It's also fine that `signed_url_cache` is keyed by document id alone, with no user id in the key: the ownership check in `_get_owned_document()` (see [Per-user document isolation](#per-user-document-isolation)) always runs *before* the cache lookup, so a user who doesn't own a document 404s before ever reaching the cache for it.
- **Verified, not just implemented** (`backend/tests/test_caching.py`, `test_cache_unit.py`): a direct test proves an actual cache *hit* by mutating the DB directly (bypassing the API, so no invalidation fires) and confirming the next `GET /documents` call still returns the pre-mutation (stale) response, not a fresh query — a test that only checked "the same data comes back" wouldn't actually prove caching is happening versus just querying twice. A second set of tests proves invalidation by performing a real upload/delete through the API and confirming the *next* read reflects it immediately. The signed-URL cache is proven by mocking `create_signed_url` with a call counter and asserting it's only invoked once across two requests. `test_cache_unit.py` tests `TTLCache` in isolation, including real expiry (a 0.05s TTL cache entry is confirmed gone after a 0.1s sleep — fast enough to run in a normal test suite without waiting out a real 60s TTL). Also verified live against the real Supabase-backed deployment: uploading a real document made it appear in `GET /documents` immediately (cache invalidation), and two real `GET /documents/{id}/download-url` calls one second apart returned the byte-for-byte identical signed URL (proving the second call never reached Supabase Storage at all).

## Background processing

The single most important structural change flagged since early in this project: `POST /documents/upload` used to run the entire extract → classify → structure pipeline (OCR plus up to two Groq round-trips) **inline**, holding the HTTP request open the whole time — a large scanned PDF could keep a request (and the worker handling it) tied up for many seconds. It's now a background task.

- **`backend/main.py`**: `upload_document` validates the file, uploads it to Storage, inserts the `documents` row (`status="uploaded"`), and **returns immediately** — that row, exactly as inserted, nothing more. `status="uploaded"` is now a real, observable state a client can actually see in a response, not (as before) an instant the row passed through before the same request finished the whole pipeline synchronously. The pipeline itself runs via `background_tasks.add_task(_process_document_in_background, document.id)` (FastAPI's `BackgroundTasks` — plenty for this scale; see below for when that stops being true).
- **`_process_document_in_background`** opens its **own** fresh `SessionLocal()` rather than reusing the request's `Depends(get_db)` session, which FastAPI's own docs warn against handing to a background task — that session is scoped to (and torn down with) the request. It looks the document back up by id (handling the case where it was deleted in the gap between the row being created and the task actually running), calls the same `processing.process_document()` used before, and wraps the whole thing in a last-resort `try/except` that logs via `logger.exception(...)` (see [Structured logging](#structured-logging)) — `process_document`/`classify_and_structure` already catch and record every *expected* failure mode as a `*_failed` status, so this is only a net for something truly unexpected (e.g. a DB connectivity blip), ensuring a background failure is never silently lost.
- **Why `BackgroundTasks` and not a real queue**: Starlette runs a plain (non-`async def`) background task via `run_in_threadpool` — offloaded to a worker thread, not blocking the event loop, so the server stays responsive to other requests while it runs. That's enough to fix the actual problem (a slow upload no longer holds its own request open, and doesn't block anyone else's request either) without adding new infrastructure. **What it doesn't give you**: tasks aren't persisted anywhere — if the process restarts or crashes mid-task, that task is just gone (no retry, no dead-letter queue), and there's no way to inspect a backlog or fan work out across multiple processes/machines. **Celery + Redis (or an equivalent, e.g. `arq`, RQ) is the natural next step** once any of that starts to matter — most likely triggered by wanting to run more than one backend process/instance (at which point `BackgroundTasks` also stops sharing state usefully with the in-process caches above and `slowapi`'s rate-limit storage, all three of which have the exact same "fine for one process, needs Redis for more than one" ceiling), or by upload volume high enough that losing an in-flight task to a restart becomes a real, not theoretical, cost.
- **Frontend polling** (`app/(app)/upload/page.tsx`): since the upload response is no longer the final word, the page now polls `GET /documents/{id}` every 2 seconds (`pollDocumentStatus`) after the initial upload response comes back, updating the same 4-step pipeline card live, until a terminal status (`processed`/`extraction_failed`/`classification_failed`/`structuring_failed`) shows up or `MAX_POLL_ATTEMPTS` (90 — three minutes) is hit, at which point it stops polling and shows a "taking longer than expected" note rather than spinning forever. A transient poll failure (network hiccup) doesn't abandon the loop — it just retries on the same schedule, since the pipeline is very likely still succeeding server-side regardless. Polling stops on unmount too (navigating away mid-upload), via a `useEffect` cleanup.
- **Verified live against the real deployment, not just mocked tests**: uploaded a real PDF with genuine invoice text — the upload response came back in ~3s (Storage upload time only) with `status: "uploaded"` and every other field `null`; polling `GET /documents/{id}` showed `status: "processed"` within the next 2 seconds, with real Groq-classified `category`, real `classification_reasoning`, and real `extracted_json` (vendor/invoice number/due date/amount all correctly extracted, `deadline_date` correctly mapped from `due_date`) — end to end through actual Storage, actual Tesseract/PyMuPDF extraction, and actual Groq calls, not stand-ins. Separately confirmed against a throwaway test server that a concurrent request to a *different* endpoint gets a fast response while a slow background task is still running — proving the event loop genuinely isn't blocked, not just that the upload response itself returns quickly.
- **`POST /documents/{id}/reprocess` was deliberately left synchronous** — it re-runs classify+structure only (no OCR), it's a rarer, manually-triggered action rather than the hot path, and backgrounding it would need the same polling treatment added to the document detail page too. Worth revisiting together with a real task queue if reprocessing ever becomes a hot path in its own right; not required by this phase's stated scope (upload specifically).

## Per-user document isolation

Until this phase, every authenticated user could see, download, delete, reprocess, or chat with *every* document in the system — a real data-leak risk once there's more than one real account, and one this project had already flagged (see the earlier notes throughout this file about "no per-user ownership" that this section supersedes). Documents are now genuinely owned, and every endpoint enforces it.

**Schema change** (`documents.user_id`, `models.py`, `migrations/versions/0008_add_documents_user_id_column.py` + `0009_make_documents_user_id_not_null.py`): a `uuid` column, `ForeignKey("users.id", ondelete="CASCADE")`, indexed, ultimately `NOT NULL` — added as two migrations rather than one because the real DB already had rows with no owner:

1. **`0008`**: adds the column **nullable**, with the FK and index, so it can land without touching existing rows.
2. **One-time backfill** (not a migration — a real data fix run directly against the live Supabase DB, not something a portable migration script should hardcode): before running it, the two accounts in the real `users` table were surfaced and **confirmed with the user** which one should own the 3 pre-existing documents, since "the first/only real user" turned out not to match reality — there were two accounts, one clearly a stray test account (`perf-test@example.com`) neither created nor recognized from this session's own cleanup, the other a real personal account (`yashverma612003@gmail.com`, "Yash Verma", matching this dev machine's own Windows username). Confirmed target: **`10e07133-5cbc-48be-bb99-4a2b1bd343d8`** (`yashverma612003@gmail.com`). `UPDATE documents SET user_id = '10e07133-...' WHERE user_id IS NULL` — backfilled exactly 3 rows, verified by re-querying immediately after.
3. **`0009`**: alters the column to `NOT NULL`, now that every row has an owner.

**Every document endpoint is now scoped to the requesting user** (`main.py`):

- `GET /documents`, `GET /documents/deadlines` — the base query now filters on `Document.user_id == current_user.id` in addition to their existing category/date/urgency filters.
- `GET /documents/{id}`, `DELETE /documents/{id}`, `POST /documents/{id}/reprocess`, `POST /documents/{id}/chat`, `GET /documents/{id}/download-url` — all five now go through a new shared helper, `_get_owned_document(db, document_id, current_user)`, instead of each repeating its own `db.query(Document).filter(Document.id == document_id).first()`. Filtering by **both** `id` and `user_id` in the same query means a document belonging to someone else is indistinguishable from one that doesn't exist — a 404 either way, **never a 403**, so a document's existence is never leaked to a user who doesn't own it. One helper instead of five copies of the same filter also means this can't silently drift out of sync on one of the five if a future change touches only some of them.
- `POST /documents/upload` — the created `Document` row now sets `user_id=current_user.id`, so ownership is established at the moment of creation, not bolted on after.
- `DELETE /auth/me` — see [Settings](#settings)'s updated note: account deletion now explicitly deletes everything the user owns (Storage objects, then DB rows) before deleting the user row.

**Caching** (see [Caching](#caching)): `documents_cache`/`deadlines_cache` were already keyed by user id (added defensively back in the caching phase, before this ownership model existed) — this phase is what makes that keying load-bearing rather than a hypothetical. `signed_url_cache` stays keyed by document id alone; that's still correct because `_get_owned_document()`'s ownership check always runs *before* the cache lookup in `get_document_download_url`, so a non-owner 404s before ever reaching the cache.

**Tests** (`backend/tests/test_isolation.py`, 10 tests): registers two real users, has one upload a real document (through the actual upload endpoint, not inserted directly, so ownership is set exactly the way production sets it), and confirms the other user gets a 404 — not a stale row, not a 403 — from `GET /documents/{id}`, `DELETE`, `reprocess`, `chat`, and `download-url`, and that the document never appears in their `GET /documents` or `GET /documents/deadlines`. Also confirms the owning user still has full normal access to their own document (isolation isn't accidentally over-broad), that `documents_cache` genuinely keeps two users' entries independent (not just "the query is right so the cache incidentally looks right"), and that deleting an account deletes its own documents. Existing tests that construct `Document` rows directly (`test_deadlines.py`, `test_caching.py`) needed a `user_id` threaded through — `_make_doc()` in both files now takes it as a required parameter, sourced from a new `current_user_id` fixture that calls the real `GET /auth/me` rather than reaching into the JWT by hand.

**Verified live against the real deployment, migration and all** — not just against the test suite: applied `0008`, ran the confirmed backfill, applied `0009`, then re-queried the real `documents` table directly to confirm all 3 rows still had the correct `user_id` and nothing was lost. Registered two fresh throwaway users against the live backend and confirmed neither could see the 3 real (Yash Verma-owned) documents in their own `GET /documents`. Had one throwaway user upload a real document, then confirmed the other got a 404 from all five single-document endpoints, that the owner could still access it normally (200s on `GET`/`download-url`), and that deleting the uploader's account correctly cascade-deleted that document (confirmed absent via a direct DB query afterward) while leaving the real account's 3 documents completely untouched.

## Security audit

A full audit re-covering confirmed gaps from earlier phases plus areas never previously reviewed (Analytics/Copilot/Templates' AI-tool-calling code, every upload path added since Phase 11, Storage key construction, dependency CVEs, DPDP Act 2023 compliance). Every finding below was verified empirically against the real app/real Supabase project/real dependency scanners — not assumed from reading code alone. Findings are listed by severity; critical/high were fixed immediately, medium/low are recommendations only.

### Critical

- **Storage path traversal, confirmed live against the real Supabase project**: uploading a test object with a key containing `../../` landed the object at the bucket root, outside its intended prefix — Supabase Storage genuinely resolves `..` segments in an object key rather than treating it as an opaque string. Several storage-key constructions embedded user-controlled upload filenames directly: `signature_router.py`'s `sign_document()` (`output_filename = f"signed_{document.filename}"` fed into `storage_path`) and 6 of `tools_router.py`'s endpoints via `tools_common._build_tool_storage_key(user_id, output_filename)` (`compress-pdf`, `pdf-to-docx`, `docx-to-pdf`, `convert-image`, `resize-image`, `ocr-pdf` — `merge-pdf`/`split-pdf` use fixed/server-generated names and were never affected). A crafted upload filename could make a tool's output land outside the user's own Storage prefix. **Fixed**: `_build_tool_storage_key()` now derives the key from a fresh UUID plus only the file's own extension (`Path(output_filename).suffix` — safe even against a hostile input, since `.suffix` never returns a string containing `/` regardless of how many `../` segments precede it); `sign_document()`'s `storage_path` no longer embeds `output_filename` at all (signing only ever produces a PDF, so the extension is simply hardcoded). `output_filename`/`document.filename` are unchanged as *display* values (`ToolFile.output_filename`, `SignedDocument.filename`) — only their use as a Storage *key* was the bug.
- **Frontend: Next.js 14.2.15 has 2 unauthenticated RCE CVEs** (`GHSA-p293-qw3h-jr36` — Windows-hosted servers; `GHSA-2xp9-vwfh-vxw4` — AVIF in the Image Optimization API) plus a high-severity SSRF-via-`rewrites()` and a high-severity `postcss` path-traversal, all bundled in the currently pinned version (confirmed via `npm audit`). Checked applicability directly rather than assuming worst-case: the Windows RCE doesn't apply (this app deploys to Render's Linux Docker container, not Windows — see [Deployment](#deployment-render)); no `rewrites()` are configured anywhere in `next.config.mjs`, so the SSRF vector is inapplicable; the AVIF image-optimizer RCE's exposure is reduced (`next/image` is never imported anywhere in this app, no `remotePatterns` configured) but not conclusively eliminated, since the framework's built-in `/_next/image` route likely still exists regardless of whether app code uses the component. **The full fix is a major Next.js version bump (14→15/16)** — `npm audit fix` confirms no non-breaking fix exists (`fixAvailable` requires `next@16.3.6`, `isSemVerMajor: true`). Deliberately **not** attempted blind inside this audit: the blast radius (App Router behavior, and this app's own Sentry instrumentation setup, which CLAUDE.md's Error tracking section documents as genuinely version-14-specific — `instrumentationHook`) is too large to safely complete and fully regression-test in one pass. **Immediate stopgap applied instead**: `next.config.mjs` now sets `images: { unoptimized: true }`, disabling the built-in image optimizer outright — a zero-risk, zero-functional-loss change given `next/image` is never used — closing the AVIF RCE surface specifically ahead of the real fix. Verified: production build (`npm run build`) succeeds with identical route sizes, and the full Playwright e2e suite (8/8) still passes. **The Next.js major-version upgrade itself is a separate, larger recommended task**, not completed here.

### High

- **`tool_files`' Storage objects were permanently orphaned on account deletion.** `delete_account()` explicitly cleaned up `documents` and `signed_documents` Storage objects (see [Per-user document isolation](#per-user-document-isolation)/[E-signature](#e-signature)) but never touched `ToolFile` rows at all. `tool_files.user_id` has `ON DELETE CASCADE`, so `db.delete(current_user)` silently removed every one of that user's `ToolFile` rows at the DB level *before* the opportunistic retention sweep (`cleanup_expired_tool_files`, which only ever looks at rows still *in* the table) could ever see them again — their Storage objects then had no code path that would ever find or delete them. A real compliance gap: "delete my account" wasn't actually deleting this data, just the row that pointed at it. **Fixed**: `delete_account()` now explicitly deletes every owned `ToolFile`'s Storage object (best-effort, same pattern as documents/signed_documents) before the row cascades away.
- **`POST /documents/{id}/chat` and `POST /documents/{id}/reprocess` had zero rate limiting** — every other Groq-calling endpoint in the app (login, upload, all 7 `/tools/*` transforms, editor chat, copilot chat, analytics generate, both templates endpoints, document signing) has one; these two didn't. A single authenticated user could hammer either endlessly — real Groq quota/cost exposure with no defense. **Fixed**: both now share the same `20/hour` per-user limit (`user_or_ip_key`) as every other AI-calling endpoint.
- **Changing your password didn't invalidate existing JWTs.** By design this app's tokens were never tied to the password hash (documented reasoning: avoids extra complexity for the "wrong current password" case), but the real consequence is a stolen token stayed fully valid for its entire ~24h lifetime even after the legitimate user noticed the compromise and changed their password. **Fixed**: `users.token_version` (new column, migration `0016_add_token_version_to_users`, default `0`) is embedded as the `"tv"` claim in every issued JWT (`auth.create_access_token()`) and checked in `auth.get_current_user()` — a mismatch is rejected identically to any other invalid token (same `credentials_exception`, so a version mismatch doesn't leak *why* a token is invalid). `POST /auth/change-password` bumps `current_user.token_version`, immediately invalidating every token issued before that moment. A token issued before this feature existed (no `"tv"` claim at all) defaults to `0` via `payload.get("tv", 0)`, matching a fresh user's own default column value — so this shipped with zero forced logouts. This also lays the groundwork for a real "log out all other sessions" button later (see Medium findings below).
- **Outdated backend dependencies with real, patchable CVEs**: `pip-audit` found 30 known advisories across `starlette` 0.38.6 (multiple DoS-class CVEs — directly relevant, this app is upload-heavy), `python-multipart` 0.0.9 (multiple DoS-class CVEs — every multipart upload endpoint in the app depends on this), and `python-dotenv` 1.0.1. **Fixed**: upgraded to `fastapi==0.141.1`, `starlette==1.3.1` (pinned explicitly — `fastapi` alone resolves to an older-but-still-vulnerable `starlette==0.50.0` unless pinned up further), `python-multipart==0.0.32`, `python-dotenv==1.2.3`. `pip-audit` now reports zero known vulnerabilities across both `requirements.txt` and `requirements-dev.txt`. Verified: the full 186-test suite (pre-audit count) passed unchanged after the upgrade, with no code changes needed anywhere in the app.
- **No startup validation that `JWT_SECRET_KEY` is set or sufficiently strong** — contradicting this file's own prior claim ("the app won't safely start without a real value"). Verified directly that this was actually false: `jwt.encode(payload, None, algorithm="HS256")` raises `TypeError`, and `jwt.encode(payload, "", ...)` raises `InvalidKeyError` — meaning an unset/empty key let the app boot and serve `/health` fine, only failing later, per-request, on the first login/register call, with a raw unhandled exception rather than a clean startup failure. The **currently deployed** value is strong (verified directly: 43 characters, shaped exactly like `secrets.token_urlsafe(32)`'s output, ~256 bits of entropy) — no live exposure today, but the missing guard was real. **Fixed**: `config._validate_jwt_secret_key()` now raises `RuntimeError` at import time (before the app can serve a single request) if the key is missing or under 32 characters — a floor matching this app's own documented generation method, not a new requirement invented for this fix.

### Audit log (new)

No record existed of who accessed/downloaded/deleted/signed/generated which document, when — a real requirement once real client-confidential data is at stake, not optional polish. **Added**: a new `audit_logs` table (`models.AuditLog`, migration `0017_create_audit_logs_table`) — `user_id` (`ON DELETE SET NULL`, deliberately **not** `CASCADE`) plus a `user_email` snapshot column captured at write time, so a log entry survives and stays meaningful after the account itself is later deleted (the entire point of an audit trail). No IP address is captured, consistent with this app's existing Sentry `send_default_pii=False` convention of not collecting more than it needs. `audit_log.record(db, user, action, resource_type, resource_id, detail=None)` is a thin, best-effort helper (a write failure never fails the real request it's describing, same convention as this app's Storage-cleanup calls) — wired into `GET /documents/{id}` (`"view"`), `GET /documents/{id}/download-url` (`"download"`), `DELETE /documents/{id}` (`"delete"`), `POST /documents/{id}/sign` (`"sign"`), `POST /templates/{id}/generate` (`"generate"`), and `DELETE /auth/me` (a single summary `"delete_account"` row noting how many documents/signed documents/tool files were removed, rather than one row per resource). Deliberately **not** wired into list endpoints (`GET /documents`) or the AI chat endpoints — the audit trail is "who touched *this specific document*," not a log of every read of the whole registry.

**Tests** (`backend/tests/test_security_audit.py`, 17 tests) — covers all of the above: `_build_tool_storage_key()` never emits a `..`-containing key and correctly extracts just the extension from a hostile `output_filename`; a real sign-document call against a document with a deliberately path-traversal-shaped filename produces a clean `storage_path` (the crafted filename still shows up correctly in the *display* `SignedDocument.filename`, proving only the Storage-key use was fixed, not the data itself); a real account deletion with a real merged-PDF tool output confirms the Storage object is actually gone afterward (not just the DB row); `/documents/{id}/chat`, `/documents/{id}/reprocess`, and `POST /auth/signature` each hit a real 429 on their 21st call within an hour; changing a password makes the old token 401 on its very next use while a fresh login token keeps working; `_validate_jwt_secret_key()` rejects `None`/empty/too-short values and accepts a real one; `database._connect_args_for()` omits `sslmode` for a localhost/127.0.0.1 URL and requires it for a real-shaped Supabase pooler URL; viewing → downloading → deleting a document produces exactly the three expected audit rows in order, correctly attributed; and a deleted account's own `delete_account` audit row survives with `user_id` nulled but `user_email` intact.

### Medium — recommendations, not implemented

- **`localStorage` JWT storage** (documented trade-off from the original Authentication phase): an XSS anywhere in the app could exfiltrate the token. Real confidential financial/identity data now flowing through the app changes the risk calculus from when this was first accepted. A full httpOnly-cookie migration is invasive (CORS `allow_credentials`, `SameSite`, every `fetch`/XHR call site across the frontend) — recommend scheduling as its own dedicated phase with full regression testing, not folding into this audit.
- **No general "log out all other sessions" beyond the password-change fix above.** A lost/stolen device has no way to be revoked before natural token expiry. The new `token_version` column makes a real "log out everywhere" Settings button a small, well-scoped follow-up (bump the version directly, independent of a password change).
- **No field-level encryption for GSTIN/PAN/bank account numbers inside `extracted_json`**, beyond Supabase's disk-level encryption-at-rest. Assessed, not implemented: real column-level encryption needs a KMS/key-management story, and would break both Copilot's full-text search and Analytics' 3 aggregation tools (both read `extracted_json` fields directly, in plaintext, by design). DPDP Rules 2025's Rule 6 "reasonable security safeguards" language requires encryption in transit and at rest (which Supabase already provides) — it does not specifically mandate field-level encryption. Recommend revisiting only if this scales beyond single-tenant-per-account toward many firms' data at real volume.
- ~~No explicit `sslmode=require` on the Postgres connection string~~ — **fixed on request.** `database._connect_args_for(db_url)` now returns `{"sslmode": "require"}` for any non-local connection string, and `{}` (unchanged libpq default) when `"localhost"`/`"127.0.0.1"` appears in the URL — the local/test Postgres container has no SSL configured at all and would otherwise fail to connect. Verified live against the real Supabase database (not just the test suite): connected successfully with `sslmode=require` actually in effect (`_connect_args_for` returns `{"sslmode": "require"}` for the real `SUPABASE_DB_URL`, confirmed `SELECT 1` still succeeds through it).
- ~~`POST /auth/signature` has no rate limit~~ — **fixed on request.** Now shares the same `20/hour` per-user `SIGN_RATE_LIMIT` (`user_or_ip_key`) as `POST /documents/{id}/sign` and every other upload endpoint in the app.

### Research findings (reported, not code changes)

- **Groq's data policy** (`console.groq.com/docs/your-data`; Services Agreement §4.2): Groq does **not** train on customer inputs/outputs by contract, absent explicit opt-in. Inference requests are **not retained by default**; if retained at all (system reliability, or investigating suspected abuse), it's for **up to 30 days**. A self-serve **Zero Data Retention** toggle exists in Groq's own dashboard (Data Controls). Data resides in **US**-based GCP infrastructure. Given GSTIN/PAN/bank details flow through every structured-extraction/chat/copilot/analytics Groq call by the nature of the product, **recommend enabling Zero Data Retention in the Groq dashboard** — a dashboard setting, not something controllable from this app's own code.
- **DPDP Act 2023 / DPDP Rules 2025** (notified 13 Nov 2025; Data Protection Board of India now exists; full compliance required by ~Nov 2026 or May 2027, timeline still being finalized): as a data fiduciary processing PAN/GSTIN/financial data for real firms, this app would need — **before onboarding any real firm's data** — a plain-language privacy notice at the point of collection, "free, specific, informed, unambiguous" consent, mechanisms honoring data-principal access/correction/erasure rights, 72-hour breach notification to affected individuals (immediately to the Data Protection Board), and Rule 6's mandatory safeguards (encryption in transit/at rest — already true via Supabase; access controls; 1-year log retention — the new audit log above is a start; incident response procedures; processor agreements). Penalties are steep (₹250cr for failing reasonable security safeguards, ₹200cr for breach-notification failures, ₹10,000 for an individual rights violation). **A real, lawyer-reviewed privacy policy is a genuine prerequisite before any real firm's data goes into this app** — flagged in an earlier phase as a future concern; this audit confirms it is now a concrete blocker, not a hypothetical one.

## Performance notes

Investigated a reported "everything feels sluggish" complaint (login, page loads, navigation) by measuring each of four suspected causes individually rather than guessing:

- **`GET /auth/me` re-fetched on navigation — not a real cause.** `AuthProvider`'s fetch runs in a `useEffect(..., [])` that only fires once per mount (`frontend/lib/auth-context.tsx`); since `AuthProvider` lives in the root layout and Next.js App Router doesn't remount ancestor layouts on client-side `<Link>`/`router.push` navigation, this genuinely only runs once per page load, not per route.
- **`GET /documents` over-fetching — real, fixed.** See [API endpoints](#api-endpoints) and the [Indexes](#database) note above — `raw_text` (often 10-25KB+ per document) was included in every list response despite no list view reading it; measured ~89% of a real payload's bytes. Both list endpoints now return `DocumentListOut` (no `raw_text`); the single-document detail fetch is unaffected.
- **Missing indexes — real, fixed.** `documents` had no index beyond the primary key despite `category`/`deadline_date`/`upload_date` being filtered/sorted on every list call. Added in `0007_add_documents_indexes`.
- **Next.js dev mode (`npm run dev`) — real, and expected, not a bug.** Measured directly: first visit to a route in a freshly-started dev server takes 2.2–3.4s (webpack compiling that route on demand); the same route on a second visit takes 25–50ms — a 40-130x difference. `dev.ps1`/`dev.sh` (the documented local workflow) both run dev mode for the frontend, so this is expected during local development, especially for `/login` (always the first, and therefore always-cold, route in a fresh session). It goes away with a production build: `npm run build && npm run start` (frontend) and running `uvicorn` without `--reload` (backend). Don't chase this as a bug during local dev testing — only worth a second look if a *production* build still shows multi-second first-loads.

## Known free-tier limits to watch

- **Groq**: rate limits around ~30 requests/minute on free tier — batch or throttle AI calls accordingly.
- **Supabase**: free tier project auto-pauses after a period of inactivity — first request after a pause will be slow or fail until it wakes up.
- **Render**: both services are on the free plan, which spins down after ~15 minutes of no traffic and cold-starts (10s–60s+) on the next request. **This is expected during solo/manual testing** — if the dashboard or an upload seems to hang on the first request after a break, it's very likely a cold start, not a bug. Don't chase it as an error unless it fails to come up at all after ~a minute.
- **Supabase Storage**: shares the same free-tier project quota as the database (roughly 1GB of file storage) — much smaller than R2's old 10GB cap, so watch usage as documents accumulate more closely than before.
